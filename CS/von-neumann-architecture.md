# 폰 노이만 구조

# [CS] 컴퓨터 구조의 큰 그림: 폰 노이만 구조와 프로그램 실행의 본질

오늘날 우리는 인터넷을 통해 프로그램이나 이미지, 동영상을 다운로드하고 그 저장된 파일들을 실행한다. 그렇다면 다운로드한 파일은 컴퓨터 어디에 저장되며, 더블클릭하는 순간 내부에서 어떤 과정을 거쳐 실행되는 걸까?

이 질문에 대한 답은 현대 컴퓨터의 설계 철학인 **폰 노이만 구조(Von Neumann Architecture)** 에 있다.

---

## 1. 폰 노이만 구조와 핵심 하드웨어 구성 요소

폰 노이만 구조란 **"모든 프로그램과 데이터는 주기억장치(메모리)에 먼저 올라가고, CPU가 버스를 통해 이를 하나씩 가져와 순차적으로 실행한다"** 라는 **프로그램 내장 방식(Stored-Program Concept)** 을 말한다.

폰 노이만 구조 이전의 초기 컴퓨터(예: 에니악 ENIAC)는 하드웨어 배선 자체가 프로그램이었다. 새로운 연산을 하려면 사람이 직접 전선을 뽑아 다시 꽂고 스위치를 조작해야만 했다. 폰 노이만은 하드웨어는 그대로 두고 메모리에 올라가는 소프트웨어(명령어와 데이터)만 교체하여 실행하는 구조를 고안했고, 스마트폰부터 AWS 클라우드 서버까지 현대의 모든 범용 컴퓨터는 이 원리로 동작한다.

폰 노이만 구조는 크게 **CPU, 주기억장치, 보조기억장치, 시스템 버스(그리고 입출력 제어기)** 로 이루어져 있다.

### ① CPU (중앙처리장치)
운영체제(OS)와 소프트웨어의 명령어를 읽고(Fetch) 해석(Decode)하며, 실제 연산 및 실행(Execute)을 담당하는 컴퓨터의 두뇌이다.
* **제어장치 (CU, Control Unit):** 명령어를 해석하고 컴퓨터의 각 부품에 제어 신호(전기 신호)를 보내 지휘한다.
* **산술논리연산장치 (ALU, Arithmetic Logic Unit):** 덧셈, 뺄셈 같은 산술 연산과 AND, OR 같은 논리 연산을 수행하는 계산기이다.
* **레지스터 (Register):** CPU 내부에 존재하는 초고속 임시 저장 공간이다. 현재 실행할 명령어나 연산 직전의 데이터를 극소량 보관한다(PC, IR, MAR, MBR 등).

> **💡 CPU와 운영체제(OS)의 관계는 무엇인가?**
> 비유하자면 **CPU는 '초인적인 속도로 일하는 육체(일꾼)'** 이고, **운영체제(OS)는 그 일꾼에게 작업 순서를 지시하는 '현장 소장(소프트웨어)'** 이다. 사실 OS조차도 디스크에 저장되어 있다가 부팅 시 RAM의 커널 영역에 올라오는 하나의 '프로그램'이다. CPU는 스스로 어떤 프로그램을 먼저 실행할지 판단하지 못한다. 대신 CPU가 OS의 스케줄링 코드를 읽어들여 실행함으로써, 결과적으로 OS가 CPU와 하드웨어 자원을 통제하고 일반 프로그램들에게 나눠주는 구조로 동작한다.

### ② 주기억장치 (Main Memory)
컴퓨터가 현재 실행 중인 프로그램의 명령어와 데이터를 임시로 보관하는 핵심 하드웨어이다. CPU가 메모리 번지(Address)를 통해 직접 접근하여 데이터를 읽고 쓸 수 있기 때문에 컴퓨터의 전반적인 작업 속도에 결정적인 영향을 미친다.
* **특징:** 속도가 매우 빠르지만, 전원이 꺼지면 데이터가 모두 날아가는 **휘발성(Volatile)** 메모리이며 보조기억장치에 비해 용량이 적고 가격이 비싸다.
* **종류:**
  * **RAM (Random Access Memory):** 실행 중인 프로그램이 올라가는 실제 작업 공간이다. 어느 위치에 있는 데이터든 동일한 속도로 즉시 접근(Random Access)할 수 있다.
  * **ROM (Read Only Memory):** 전원이 꺼져도 지워지지 않는 비휘발성 메모리로, 컴퓨터 부팅 시 가장 먼저 실행되어야 하는 기본 입출력 시스템(BIOS/UEFI) 등이 저장되어 있다.

### ③ 보조기억장치 (Secondary Storage)
전원이 꺼지면 데이터가 사라지는 주기억장치(RAM)의 한계를 보완하여, 데이터를 반영구적으로 안전하게 보관하는 장치이다.
* **특징:** 전원이 꺼져도 데이터가 유지되는 **비휘발성(Non-Volatile)** 매체이며, 용량이 크고 기가바이트(GB)당 가격이 저렴하지만 주기억장치보다 속도가 훨씬 느리다.
* **종류:**
  * **SSD (Solid State Drive):** 낸드 플래시(반도체 칩)를 이용해 전기적으로 데이터를 저장하는 현대 컴퓨터의 핵심 저장장치이다. 물리적으로 움직이는 부품이 없어 속도가 빠르고 소음이 없으며 충격에 강하다.
  * **HDD (Hard Disk Drive):** 자성 물질이 입혀진 금속 원판(플래터)을 물리적으로 회전시켜 데이터를 읽고 쓰는 전통적인 장치이다. SSD에 비해 속도는 느리지만 가격 대비 용량이 커서 대용량 데이터 백업용으로 여전히 쓰인다.
  * **기타 매체:** USB 플래시 드라이브, 외장 하드, SD 카드 등.

> **💡 CPU와 보조기억장치 사이에는 무엇이 더 존재하는가? (I/O 제어기와 메모리 계층)**
> 두 가지 관점에서 중간 매개체가 존재한다.
> 1. **입출력 제어기 (I/O Controller / 디바이스 컨트롤러):** 보조기억장치(SSD/HDD)는 시스템 버스에 그냥 꽂는다고 CPU와 바로 대화할 수 없다. CPU의 전기 신호 규격과 디스크의 제어 방식이 완전히 다르기 때문에, 중간에 **입출력 제어기(SATA/NVMe 컨트롤러 등)** 가 위치하여 CPU의 명령을 해석하고 디스크의 데이터를 대신 읽어들인다.
> 2. **메모리 계층 구조 (Memory Hierarchy):** 속도 차이 관점에서 보면 CPU와 보조기억장치 사이에는 수많은 완충 지대가 놓여 있다.
>    `[CPU 프로세서 내부: 레지스터 <-> L1/L2/L3 캐시 메모리]` $\leftrightarrow$ `[주기억장치: RAM]` $\leftrightarrow$ `[보조기억장치: SSD/HDD (가상 메모리 Page File/Swap 포함)]`
>    CPU 바로 옆에는 RAM보다도 훨씬 빠른 **캐시 메모리(SRAM)** 가 L1, L2, L3 계층으로 붙어 있어 CPU가 느린 RAM을 매번 기다리지 않도록 자주 쓰는 데이터를 미리 당겨와 보관한다.

### ④ 시스템 버스 (System Bus)
컴퓨터 내부에서 CPU, 주기억장치(RAM), 입출력 제어기(보조기억장치 연결) 등이 서로 데이터와 신호를 주고받는 물리적인 공유 통로(전선 다발)이다. 역할에 따라 3가지로 나뉜다.
* **주소 버스 (Address Bus):** CPU가 읽거나 쓸 메모리의 '번지(주소)'를 전달하는 통로이다. CPU가 메모리나 입출력 장치로 주소를 지정하기만 하므로 **단방향**으로 동작한다.
* **데이터 버스 (Data Bus):** 실제 명령어와 데이터가 오가는 통로이다. 읽기와 쓰기가 모두 일어나므로 **양방향**으로 동작한다.
* **제어 버스 (Control Bus):** CPU가 "지금 데이터를 읽겠다(Memory Read)" 혹은 "쓰겠다(Memory Write)"와 같은 제어 신호를 보내거나, 하드웨어가 CPU에 인터럽트 신호를 보낼 때 쓰는 통로이다.

## 2. 왜 주기억장치(RAM)와 보조기억장치(SSD)를 하나로 합치지 못할까?

공부하다 보면 자연스럽게 이런 의문이 든다.
**"그냥 보조기억장치(SSD)를 RAM만큼 빠르게 만들거나, 반대로 RAM 용량을 SSD처럼 수 테라바이트(TB)로 늘려서 하나로 쓰면 안 되나? 왜 굳이 둘로 나눴을까?"**

결론부터 말하면 **반도체 물리학적인 한계와 경제적 비용(기회비용)** 때문이다.

### ① 물리적 구조의 차이 (왜 보조기억장치를 RAM만큼 빠르게 못 만드는가?)
* **RAM(DRAM):** 축전기(Capacitor)라는 아주 단순한 소자에 전하를 채우거나 비우는 방식으로 0과 1을 표현한다. 구조가 단순해서 전기가 통하는 즉시(수십 나노초, ns) 바이트 단위로 읽고 쓸 수 있다. 단, 전하가 금방 빠져나가므로 전원이 끊기면 데이터가 증발한다(휘발성).
* **SSD(NAND 플래시):** 전원이 꺼져도 전자를 가둬두기 위해 '플로팅 게이트'라는 두꺼운 절연막 안에 전자를 강제로 밀어 넣고 빼는 복잡한 물리적 과정을 거친다. 이 과정 자체가 수만 나노초(마이크로초, µs) 이상 걸리며, 특정 바이트만 골라 덮어쓸 수 없고 수천 바이트(Block/Page) 단위로 통째로 지웠다가 다시 써야 한다. 즉, **'비휘발성(영구 보존)'을 얻는 대가로 '속도와 바이트 단위 접근성'을 포기한 구조**이다.

### ② 경제적 비용과 기회비용 (왜 RAM을 보조기억장치처럼 크게 못 만드는가?)
*"속도 차이에서 발생하는 기회비용이 하드웨어 비용을 압도하기 때문에 RAM 방식을 채택했다"*라는 말은 쉽게 풀어쓰면 다음과 같다.

만약 몇만 원짜리 RAM을 아끼겠다고 CPU가 느려터진 SSD에서 프로그램을 직접 읽어서 실행하게 만들면, 수십만 원짜리 초고속 CPU는 연산을 한 번 할 때마다 디스크에서 데이터가 올 때까지 손가락만 빨며 대기해야 한다. 결국 수백만 원짜리 컴퓨터 전체가 마비 수준으로 느려진다(엄청난 **기회비용** 손실)[cite: 2].
반대로 RAM은 용량 대비 가격이 SSD보다 수십 배 비싸고 전기를 계속 먹으며, 전원을 끄면 데이터도 날아간다[cite: 2]. 따라서 모든 파일을 비싼 RAM에 영구 보관할 수는 없다.

결국 현대 컴퓨터는 **"평소에는 저렴하고 안 날아가는 넓은 창고(SSD)에 파일을 보관해 두고, 당장 실행할 프로그램만 비싸고 초고속인 작은 작업 책상(RAM)에 복사해 올려서 CPU의 속도를 100% 뽑아내자"** 라는 가장 합리적인 타협점(메모리 계층 구조)을 선택한 것이다[cite: 2].

## 3. 폰 노이만 구조의 밑바닥 동작 원리 (텍스트로 완벽 이해하기)

다이어그램을 보지 않고 글만 읽어도 머릿속에 영화처럼 그려지도록, 디스크에 있는 `game.exe` 파일을 더블클릭했을 때 컴퓨터 내부에서 벌어지는 5단계 과정을 정리한다[cite: 2].

### Step 1. 실행 명령 인입과 I/O 요청 (입출력 요청)
사용자가 마우스로 `game.exe`를 더블클릭하면 마우스 하드웨어 인터럽트가 발생해 OS(운영체제)에게 전달된다[cite: 2]. OS는 해당 파일이 보조기억장치(SSD)의 어느 위치에 저장되어 있는지 확인한 뒤, 보조기억장치 앞단의 **입출력 제어기(I/O Controller)** 에게 *"디스크에 있는 `game.exe` 데이터를 읽어서 RAM으로 올려라"*라는 I/O 요청 명령을 내린다[cite: 2].

### Step 2. 직접 메모리 접근 (DMA, Direct Memory Access)
만약 디스크에 있는 수 기가바이트짜리 파일 데이터를 CPU가 직접 한 바이트씩 읽어서 RAM으로 옮긴다면, 파일 복사하는 내내 CPU는 다른 작업을 전혀 하지 못하고 멈춰버린다[cite: 2].
이를 막기 위해 **DMA(직접 메모리 접근) 제어기**가 개입한다[cite: 2]. CPU는 DMA에게 *"디스크 어디부터 어디까지 읽어서 RAM 어디에 복사해 두고, 다 끝나면 나한테 알려줘"*라고 지시만 내리고 자기 할 일을 하러 간다. 그러면 입출력 제어기와 DMA가 CPU를 거치지 않고 시스템 버스를 통해 디스크의 프로그램 데이터를 RAM의 빈 공간으로 직접 복사하고, 완료되면 CPU에 인터럽트 신호를 보낸다[cite: 2].

> **💡 실행할 때 `.exe` 파일 전체를 전부 RAM에 복사하는 걸까? 만약 파일이 100GB인데 내 RAM이 16GB면 어떻게 실행될까?**
> **절대 파일 전체를 한 번에 RAM에 다 올리지 않는다!**
> 과거 초기 컴퓨터는 프로그램 전체를 메모리에 올렸지만, 현대 운영체제는 **가상 메모리(Virtual Memory)** 와 **요구 페이징(Demand Paging)** 이라는 기법을 사용한다.
> 100GB짜리 게임을 실행하더라도, 처음에는 당장 게임을 켜고 로고를 띄우는 데 필요한 **핵심 실행 코드 조각(Page, 보통 4KB 단위) 몇 개만 RAM에 살짝 복사**한다[cite: 2]. 그리고 게임을 진행하다가 새로운 맵이나 데이터가 필요해지면, 그때그때 필요한 조각만 디스크에서 RAM으로 가져오고 안 쓰는 조각은 지운다[cite: 2]. 이 덕분에 내 물리 RAM 용량(16GB)보다 훨씬 거대한 프로그램도 문제없이 실행할 수 있다.

### Step 3. 메모리 번지(Address) 부여와 MMU의 변환
프로그램의 명령어와 데이터가 RAM에 올라가는 순간, 각 바이트마다 `0x00001000`, `0x00001004` 같은 고유한 집 주소인 **메모리 번지(Address)** 가 부여된다[cite: 2]. CPU는 파일 이름을 알지 못하며 오직 이 메모리 번지 숫자로만 명령어와 데이터를 찾는다[cite: 2].

> **💡 여기서 등장하는 MMU(Memory Management Unit)란 무엇이고 무슨 역할을 하나?**
> **MMU(메모리 관리 장치)** 는 CPU 내부에 탑재된 하드웨어 칩으로, **'가상 주소(논리 주소)'를 실제 RAM의 '물리 주소'로 실시간 번역해 주는 통역사**이다.
> 프로그램(프로세스)이 실행될 때 OS는 각 프로그램에게 *"너한테 `0번지`부터 끝까지 깨끗한 전용 메모리를 다 줄게"*라고 가짜 주소(**가상 주소**)를 부여한다. 하지만 실제 물리적인 RAM에는 카카오톡, 크롬, 게임의 데이터 조각들이 여기저기 뒤섞여서 흩어져 올라가 있다(**물리 주소**).
> CPU가 가상 주소 `0x1000`번지를 읽으려고 할 때, CPU 안에 있는 **MMU 하드웨어**가 페이지 테이블(주소 매핑 표)을 보고 *"아, 이 프로그램의 가상 주소 `0x1000`번지는 실제 RAM에서는 `0x8FA01000`번지에 들어있구나!"*라고 나노초 단위로 변환하여 실제 RAM 번지로 신호를 보내준다.

### Step 4. CPU 버스 통신 (명령어 인출 요청)
이제 RAM에 준비가 끝났으니 CPU가 첫 번째 명령어를 가져올 차례다[cite: 2].
1. CPU 내부의 **PC(프로그램 카운터)** 라는 레지스터에는 '다음에 실행할 명령어의 메모리 번지(예: `0x1000`)'가 적혀 있다[cite: 2].
2. CPU는 이 `0x1000`이라는 번지 값을 **주소 버스**에 실어 RAM으로 보낸다[cite: 2].
3. 동시에 CPU의 제어장치는 **제어 버스**를 통해 RAM에게 *"그 번지에 있는 데이터를 읽어라(Memory Read)"*라는 전기 신호를 쏜다[cite: 2].

### Step 5. 기계어 반환 및 실행
RAM은 주소 버스로 받은 `0x1000`번지 칸을 열어서, 그 안에 들어있는 0과 1의 기계어 명령어 데이터를 **데이터 버스**에 실어 CPU로 돌려보낸다[cite: 2].
CPU는 데이터 버스를 타고 들어온 기계어를 내부의 **명령어 레지스터(IR)** 에 담은 뒤, 제어장치가 이를 해석("아, 두 숫자를 더하라는 명령이네!")하고 **연산장치(ALU)** 를 시켜 실제 계산을 완료한다[cite: 2]. 이후 PC(프로그램 카운터) 값을 다음 번지(`0x1004`)로 1칸 증가시키고, Step 4~5 과정을 프로그램이 끝날 때까지 1초에 수십억 번 반복한다[cite: 2].

## 4. 대체 아키텍처 비교와 현대 컴퓨터의 선택

왜 굳이 디스크에서 RAM으로 복사하는 폰 노이만 방식을 쓸까? 다른 대안들과 비교하면 그 이유가 명확해진다[cite: 2].

| 비교 항목 | 폰 노이만 구조 (RAM 적재 후 실행) | 디스크 직접 실행 (XIP, Execute-In-Place) | 하버드 구조 (Harvard Architecture) |
| :--- | :--- | :--- | :--- |
| **핵심 원리** | 명령어와 데이터를 **하나의 메모리(RAM)** 에 올리고 **하나의 시스템 버스**로 가져와 실행 | RAM으로 복사하지 않고 비휘발성 저장장치(ROM/플래시)에서 CPU가 직접 읽어 실행 | **명령어용 메모리/버스**와 **데이터용 메모리/버스**를 물리적으로 완전히 분리 |
| **접근 속도** | **수십 나노초(ns)** (매우 빠름) | **수십 마이크로초(µs) ~ 밀리초(ms)** (극도로 느림) | **가장 빠름** (명령어 인출과 데이터 읽기를 동시에 수행) |
| **주소 지정 단위** | **바이트(Byte) 단위** 정밀 접근 가능 | 블록(Block, 4KB) 단위로만 접근 가능 (일반 SSD/HDD는 직접 실행 자체가 불가) | 바이트/워드 단위 접근 가능 |
| **장점** | 하드웨어 구조가 단순하고, RAM만 교체/관리하면 되어 다중 프로그램 실행에 유리함 | RAM 로딩 시간이 없고 메모리 칩 비용을 아낄 수 있음 | 버스가 2개라 명령어와 데이터가 부딪히는 **'폰 노이만 병목'** 이 원천 해결됨 |
| **단점** | 버스가 1개뿐이라 명령어와 데이터를 동시에 가져올 수 없음 (**폰 노이만 병목 현상**) | CPU가 느린 저장장치를 기다리느라 연산 성능이 처참하게 추락함 | 회로와 버스 배선이 2배로 복잡해져 메인보드 단가와 칩 면적이 크게 증가함 |
| **주요 사용처** | **현대 범용 컴퓨터의 메인보드(CPU ↔ RAM 구간)** | 소형 임베디드 기기, 공유기 부트로더, 특수 NOR 플래시 메모리 | **현대 CPU 내부의 L1 캐시 구조**, DSP(디지털 신호 처리기) |

### 현대 컴퓨터는 '폰 노이만 + 하버드'의 하이브리드 구조다
폰 노이만 구조는 명령어와 데이터가 하나의 버스를 공유하기 때문에, 명령어를 가져오는 동안에는 데이터를 가져올 수 없는 **폰 노이만 병목(Von Neumann Bottleneck)** 이라는 치명적인 한계가 있다[cite: 2].
이를 해결하기 위해 현대 컴퓨터는 두 구조를 섞어 쓴다[cite: 2].
* **컴퓨터 외부 (CPU ↔ RAM 구간):** 회로 복잡도와 비용을 줄이기 위해 **폰 노이만 구조**를 따른다[cite: 2].
* **CPU 코어 내부 (L1 캐시 구간):** 속도가 생명인 CPU 내부의 L1 캐시는 **'명령어 전용 캐시(L1i)'** 와 **'데이터 전용 캐시(L1d)'** 로 통로를 물리적으로 쪼개어 동시에 접근하는 **하버드 구조**를 채택하고 있다[cite: 2].

## 5. 실무에서 겪을 수 있는 상황: 스왑(Swap) 메모리의 함정

오늘 정리한 폰 노이만 구조의 대원칙(**"CPU는 오직 RAM에 올라온 데이터만 읽고 처리할 수 있다"**)을 모르면 실무 서버 운영에서 큰 장애를 겪게 된다[cite: 2].

### ① 문제의 배경: AI는 왜 "스왑(Swap)을 걸어라"고 했을까?
클라우드(AWS EC2 등)에서 흔히 쓰는 무료/저비용 서버(예: `t3.micro`)는 물리 RAM이 **1GB~2GB** 에 불과하다[cite: 2]. 여기에 Java Spring Boot 서버를 띄우고 DB나 Docker까지 올리면 RAM 사용량이 순식간에 90%를 넘어간다[cite: 2].

RAM이 100% 꽉 차면 리눅스 운영체제(OS)는 시스템 전체가 멈추는 것을 막기 위해 메모리를 가장 많이 먹는 프로세스(내 백엔드 서버)를 강제로 죽여버린다. 이를 **OOM Killer(Out Of Memory Killer)** 라고 부른다[cite: 2].
이때 AI나 인터넷 블로그에 해결책을 물어보면 십중팔구 다음과 같이 답한다[cite: 2]:
> *"하드디스크(SSD)의 일부 공간(예: 4GB)을 메모리처럼 쓸 수 있게 가상 메모리 영역인 **스왑 파일(Swap File)** 을 설정하세요."*[cite: 2]

개발자는 이 말을 듣고 *"1GB짜리 서버가 5GB(RAM 1GB + 스왑 4GB)짜리 서버로 업그레이드됐구나!"* 라며 안심한다[cite: 2]. 하지만 이것이 재앙의 시작이다[cite: 2].

### ② 비유로 보는 작업실의 재앙
* **CPU (천재 작업자):** 오직 자기 눈앞의 **책상(RAM)** 에 놓인 서류만 읽을 수 있다[cite: 2].
* **SSD 스왑 영역 (지하 창고):** 책상이 좁아서 당장 안 보는 서류를 임시로 빼두는 복도 끝 지하 창고이다[cite: 2]. 창고에 서류가 아무리 많아도, 작업자(CPU)가 그 서류를 읽으려면 **반드시 창고에서 꺼내 다시 책상(RAM) 위로 올려놓아야만 한다**[cite: 2].

```text
[정상 상황: 모든 데이터가 책상(RAM) 위에 있을 때]
작업자(CPU) <──(수십 나노초)──> 책상(RAM) : 손만 뻗으면 바로 서류를 읽고 초당 수천 건을 처리한다.

[스왑 발생 상황: 책상이 꽉 차서 일부 서류를 지하 창고(SSD 스왑)에 빼뒀을 때]
작업자(CPU) ── "다음 처리할 서류 어디 있어?"
OS          ── "책상이 좁아서 지하 창고(스왑)에 넣어뒀어. 내가 가서 가져올게 기다려."
작업자(CPU) ── "..." (손 놓고 멍하니 대기: I/O Wait 상태)
OS          ── 복도 끝 창고까지 걸어가서 서류를 들고 책상으로 뛰어옴 (RAM보다 수천~수만 배 느림)
```

### ③ 동시 접속자가 몰릴 때 벌어지는 악순환 (스레싱, Thrashing)
사용자가 1~2명일 때는 가끔 창고에 다녀와도 0.1초 늦어지는 수준이라 티가 안 난다. 하지만 동시 요청이 50건, 100건 몰리면 서버는 지옥에 빠진다.

1. **동시 요청 50건 유입 (왜 이때 RAM이 100% 꽉 찰까?)**
   * 웹 서버는 요청 1건을 처리할 때마다 작업용 스레드를 할당하고, 요청 JSON 데이터를 파싱해 객체로 만들며, DB에서 조회한 결과 데이터들을 메모리에 올린다(JVM Heap 및 Stack 공간 소모). 50명이 동시에 요청하면 50명분의 작업 서류 뭉치가 한꺼번에 책상(RAM) 위로 쏟아져 들어오므로 좁은 1GB 책상이 순식간에 가득 차버린다.
2. **페이지 아웃 (Page Out / Swap Out)**
   * **개념:** 물리 RAM에 빈자리가 없을 때, OS가 새로운 데이터를 올리기 위해 기존에 RAM에 올라와 있던 데이터 조각(Page)을 디스크의 스왑(Swap) 영역으로 쫓아내는 작업이다.
   * 50번째 사용자의 요청을 처리하려고, 1번 사용자의 데이터를 지하 창고(SSD)로 밀어낸다.
3. **페이지 폴트 (Page Fault) 발생**
   * **개념:** CPU가 실행하려는 명령어나 데이터가 가상 메모리 주소상으로는 존재하지만, 실제 물리 RAM에는 올라와 있지 않을 때(디스크에 있을 때) MMU 하드웨어가 발생시키는 인터럽트(예외 상황)이다.
   * 이제 다시 1번 사용자의 작업을 이어서 하려고 CPU가 데이터를 찾는데, 방금 지하 창고로 쫓겨나고 책상에 없다! **Page Fault** 가 터지면서 해당 작업은 즉시 멈추고 얼어붙는다.
4. **페이지 인 (Page In / Swap In)과 연쇄 추방**
   * **개념:** Page Fault를 해결하기 위해 OS가 디스크(스왑 영역)에 있는 데이터를 다시 물리 RAM으로 읽어 들여오는 작업이다.
   * 그런데 지금 책상(RAM)은 여전히 다른 49명의 서류로 꽉 차 있다. 1번 서류를 창고에서 가져오려면 책상에 있던 2번 사용자의 서류를 또 창고로 쫓아내야 한다.

> **💡 의문 1: "그냥 쫓아내지 말고, RAM에 올라와 있는 요청부터 하나씩 끝까지 다 처리한 다음에 다음 요청을 순서대로 받으면 안 되나? 물론 조금 느리겠지만 말이야."**
> 아주 날카로운 질문이다. 하지만 현대 운영체제(OS)와 웹 서버는 **'시분할 멀티태스킹(Time-Sharing)'** 방식으로 동작하기 때문에 그렇게 하지 않는다.
> 만약 1번 사용자의 요청이 외부 결제 API 응답이나 무거운 DB 쿼리를 기다리는 데 2초가 걸린다고 해보자. 1번이 끝날 때까지 나머지 49명을 아예 줄 세워 막아두면(순차 처리), CPU는 1번이 응답을 기다리는 2초 동안 아무 일도 안 하고 놀게 되며 뒤의 사용자들은 화면이 멈춘다.
> 그래서 OS 스케줄러는 공평한 응답성을 위해 **"0.01초씩 돌아가면서 50명의 작업을 조금씩 전부 동시에 진행시키는 방식(컨텍스트 스위칭)"** 을 쓴다. 문제는 50명의 작업이 모두 '진행 중'인 상태이다 보니, 0.01초마다 타자가 바뀔 때마다 그 타자의 서류가 책상(RAM)에 있어야 해서 끊임없이 서류를 창고와 책상 사이에서 맞교환하는 일이 벌어지는 것이다. (물론 애초에 서버 앞단에서 동시 작업 스레드 개수를 제한하여 줄을 세우는 튜닝 기법도 존재한다.)

5. **무한 교체 지옥, 스레싱 (Thrashing)**
   * 결국 서버는 실제 비즈니스 로직 연산은 거의 하지 못하고, 종일 디스크(SSD)와 RAM 사이에서 데이터를 넣었다 뺐다(Page In / Page Out) 하는 데만 모든 시간을 쏟는다.

> **💡 의문 2: "CPU가 연산을 1%도 못 하고 디스크와 RAM 사이에서 데이터만 옮긴다는 게 과장 아니고 실제로 일어나는 일인가?"**
> **과장이 아니라 실제 프로덕션 서버 장애 시 똑같이 목격되는 현상이다.**
> 물리적 시간 차이를 보면 이해가 된다. CPU가 RAM에 접근하는 시간은 약 **50나노초(ns)** 지만, SSD 스왑 파일에 접근해 데이터를 가져오는 시간은 약 **100,000나노초(100µs)** 이상으로 최소 **2,000배에서 수만 배** 느리다.
> 만약 스레싱이 발생해 명령어를 처리할 때마다 Page Fault가 터진다면, CPU는 **1초 일하고 2,000초 동안 디스크에서 데이터가 오기를 기다리며 멈춰 있는(I/O Wait) 셈**이 된다.
> 실제로 이때 리눅스 서버에 접속해 `top` 명령어로 상태를 보면, 실제 연산을 뜻하는 **CPU 사용률(`us`)은 0~1%대**로 바닥을 기는데, 디스크 입출력을 기다리는 **I/O 대기율(`wa`, I/O Wait)이 95~99%** 를 찍으며 서버의 모든 API가 타임아웃(504 Gateway Timeout)으로 죽어버린다.

### ④ 결론
스왑 메모리는 물리 RAM이 바닥났을 때 **"서버 프로세스가 즉사(OOM Kill)하는 대신, 속도가 극단적으로 느려지더라도 에러 로그를 남기거나 관리자에게 알림을 보낼 시간을 벌어주는 최후의 에어백"** 이다. 결코 공짜로 서버 RAM 용량을 늘려주는 마법의 기술이 아니다.
