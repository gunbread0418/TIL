# \[M2-2\] 연속된 메모리 배치 — 배열(Array) vs 동적 배열(Dynamic Array)

## 1. 면접 핵심 Q&A

### Q1. 배열(Array)의 인덱스 조회는 왜 O(1)이며, CPU 캐시 효율(공간 지역성) 측면에서 어떤 이점이 있는가?

**배열** 은 동일한 타입(동일한 바이트 크기)의 데이터를 메인 메모리(RAM)의 **연속된 공간에 빈틈없이 일렬로 할당** 하는 자료구조이다. 시작 메모리 번지(Base Address)와 원소 하나의 바이트 크기만 알면, 중간 원소를 일일이 탐색할 필요 없이 산술 연산 단 한 번으로 목표 번지를 즉시 찾아내는 **임의 접근(Random Access)** 이 가능하기 때문에 조회 시간 복잡도가 **O(1)** 이다.

* **목표 메모리 번지 계산 공식**: `목표 주소 = 시작 번지(Base Address) + (인덱스 × 원소 바이트 크기)`

또한 CPU가 RAM에서 데이터를 읽을 때는 변수 1개만 가져오지 않고, 물리적으로 인접한 **64바이트(1 Cache Line)** 블록을 통째로 긁어 L1/L2 캐시에 적재한다. 배열은 데이터가 메모리에 연속으로 붙어 있어 첫 번째 원소(`arr[0]`)를 읽을 때 뒤따라오는 원소(`arr[1] ~ arr[15]`)까지 캐시에 미리 올라오므로, 순회 시 **캐시 적중률(Cache Hit Rate)이 극대화되는 공간 지역성(Spatial Locality)** 의 이점을 누린다.

### Q2. 정적 배열(Static Array)과 동적 배열(Dynamic Array, Java의 ArrayList)의 차이는 무엇이며, 동적 배열의 크기 확장(Resize)은 어떻게 동작하는가?

**정적 배열(`int[]`, `String[]`)** 은 선언 시점에 크기가 고정되어 런타임에 길이를 늘리거나 줄일 수 없다. 반면 **동적 배열(Java `ArrayList`, C++ `std::vector`, Python `list`)** 은 내부적으로 정적 배열을 품고 있으면서, 데이터가 가득 차면 **더 큰 새로운 배열을 할당받아 기존 데이터를 통째로 복사(Resize)하는 방식** 으로 크기를 유연하게 확장한다.

* **Java `ArrayList`의 확장 메커니즘**: 기본 생성 시 용량(Capacity) 10으로 시작하며, 공간이 꽉 찬 상태에서 `add()`가 호출되면 기존 용량의 **약 1.5배(`oldCapacity + (oldCapacity >> 1)`)** 크기의 새 배열을 Heap에 생성하고 `System.arraycopy()`로 기존 요소들을 고속 복사한다.

* **분할 상환 시간 복잡도(Amortized O(1))**: 평소에는 빈칸에 바로 값을 넣으므로 **O(1)** 이 걸리고, 가끔 배열이 꽉 찼을 때만 **O(N)** 의 전체 복사가 발생한다. 크기를 1.5배\~2배씩 기하급수적으로 늘리면 N번 삽입하는 동안 발생하는 총 복사 횟수는 약 **2N** 회에 불과하므로, 이를 1회 삽입당 평균으로 나누면 **분할 상환 O(1)** 의 성능을 보장한다.

| 비교 항목 | 정적 원시 배열 (`int[]`) | 동적 배열 (`ArrayList<T>`) | 연결 리스트 (`LinkedList<T>`) | 불리언 배열 (`boolean[]`) | 
| ----- | ----- | ----- | ----- | ----- | 
| **메모리 물리 배치** | 연속된 메모리 공간 (값 자체 저장) | 내부 참조 배열이 연속 배치 (주소값 저장) | 힙 곳곳에 노드가 파편화되어 분산 | 연속된 메모리 공간 (1B 단위) | 
| **인덱스 조회 (`get`)** | **O(1)** (직접 산술 접근) | **O(1)** (배열 접근 후 참조 역참조) | **O(N)** (첫 노드부터 포인터 추적) | **O(1)** (초고속 바이트 접근) | 
| **맨 뒤 추가 (`add`)** | 불가 (크기 고정) | **분할 상환 O(1)** (확장 시 **O(N)**) | **O(1)** (Tail 포인터 연결 변경) | 불가 (크기 고정) | 
| **중간 삽입 / 삭제** | **O(N)** (수동 요소 이동) | **O(N)** (`System.arraycopy` 이동) | **O(N)** (위치 탐색 **O(N)** + 연결 **O(1)**) | **O(N)** (수동 요소 이동) | 
| **CPU 캐시 지역성** | **최상** (캐시 라인 100% 활용) | **우수** (참조 배열 순회 시 캐시 친화적) | **최악** (Pointer Chasing 발생) | **최상** (캐시 라인 극대화) | 
| **요소당 메모리 오버헤드** | **0 Byte** (순수 데이터만 존재) | 참조값 **4 Byte** + 미사용 여유 공간 | Node 객체 약 **24 Byte** (앞뒤 포인터 등) | **0 Byte** (요소당 1 Byte) | 

### Q3. 배열과 동적 배열에서 중간 삽입이나 삭제(특히 맨 앞 원소 삭제 `remove(0)`)가 왜 O(N)의 비용을 유발하는가?

배열은 **"모든 원소가 빈틈없이 연속으로 붙어 있어야 한다"** 는 물리적 불변식을 유지해야만 인덱스 산술 공식(`Base + i × Size`)이 성립한다.

따라서 중간 인덱스에 새 값을 끼워 넣으려면 그 뒤에 있는 모든 원소를 오른쪽으로 한 칸씩 밀어내야 하고, 반대로 중간이나 맨 앞 원소(`remove(0)`)를 삭제하면 빈자리를 메우기 위해 **뒤에 있는 모든 원소를 왼쪽으로 한 칸씩 당겨오는 물리적 메모리 복사(Shift)** 를 수행해야 한다. 원소가 N개일 때 맨 앞 원소를 삭제하면 N-1개의 데이터를 복사해야 하므로 **O(N)** 이 소요되며, 이를 루프 안에서 반복하면 **O(N²)** 성능 장애로 직결된다.

## 2. 실무 사례 (상세 해부)

### 사례 1. 대량 데이터 수집 시 초기 용량(Capacity) 미지정과 `remove(0)` 큐(Queue) 오용으로 인한 서버 멈춤

외부 결제사에서 당일 정산 데이터 10만 건을 받아와 리스트에 담은 뒤, 앞에서부터 하나씩 꺼내어 처리하는 배치 로직이다. AI가 작성해 주거나 초급 개발자가 흔히 작성하는 코드에서 두 가지 치명적인 배열 오용이 동시에 발생했다.

```
// [문제가 된 코드]
// 1. 초기 용량 미지정: 기본 크기 10짜리 배열로 시작!
List<PaymentDto> payments = new ArrayList<>(); 
for (PaymentDto item : externalApiData) { // 100,000건 반복 추가
    payments.add(item); // 용량이 찰 때마다 25번 이상 새 배열 생성 + 전체 복사 발생!
}

// 2. ArrayList를 큐(FIFO)처럼 쓰기 위해 맨 앞(0번 인덱스) 요소를 반복해서 꺼냄
while (!payments.isEmpty()) {
    PaymentDto target = payments.remove(0); // <-- 매 반복마다 남은 요소를 전부 왼쪽으로 한 칸씩 당김 (O(N))!
    process(target);
}

```

#### ① 왜 이런 현상이 발생했는가? (메모리 밑바닥 추적)

1. **첫 번째 문제 — 잦은 Resize와 GC 폭발**: `new ArrayList<>()`는 처음에 크기가 **10** 인 배열만 만든다. 여기에 10만 건을 넣으면 용량이 `10 → 15 → 22 → 33 → 49 ... → 100,000`으로 커질 때까지 **총 25번 이상 더 큰 배열을 새로 만들고 기존 데이터를 복사** 한다. 이때 이사하고 남은 헌 배열 25개는 전부 JVM Heap의 쓰레기(Garbage)가 되어 불필요한 GC(가비지 컬렉션)를 유발한다.

2. **두 번째 문제 — `remove(0)`의 메모리 당겨오기 재앙**: `ArrayList`에서 0번 인덱스를 지우면 0번 칸을 비워둘 수 없다.

   ```
   [payments.remove(0) 실행 시 메모리에서 벌어지는 일]
   삭제 전: [데이터0] [데이터1] [데이터2] ... [데이터99999]
   0번 삭제: [ 빈칸! ] [데이터1] [데이터2] ... [데이터99999] -> 배열은 빈칸을 허용하지 않음!
   강제 이동: [데이터1] ← [데이터2] ← [데이터3] ... ← [데이터99999] (99,999개를 전부 한 칸씩 앞으로 복사!)
   
   ```

   첫 번째 삭제 때 99,999개 이동, 두 번째 삭제 때 99,998개 이동... 이를 10만 번 반복하면 총 이동 횟수는 `99,999 + 99,998 + ... + 1 ≈ 5,000,000,000 (약 50억 번)`의 메모리 복사가 발생하여 **O(N²)** 으로 서버 CPU가 멈춰버린다.

#### ② 실무적 해결책

* 들어올 데이터 크기를 대략이라도 안다면 생성자에 **초기 용량(`new ArrayList<>(size)`)을 반드시 지정** 하여 배열 확장(Resize)을 0회로 차단한다.

* 앞에서부터 데이터를 꺼내는 선입선출(FIFO) 작업이 필요하다면 `ArrayList`가 아니라, 맨 앞 요소를 **O(1)** 에 꺼낼 수 있는 **`ArrayDeque`** 를 사용한다.

```
// 1. 초기 용량 10만 칸을 한 번에 할당 (Resize 및 배열 복사 0회!)
List<PaymentDto> payments = new ArrayList<>(externalApiData.size());

// 2. 맨 앞 요소를 꺼내는 작업은 원형 배열 구조인 ArrayDeque를 사용하여 O(1)로 처리!
Deque<PaymentDto> queue = new ArrayDeque<>(externalApiData);
while (!queue.isEmpty()) {
    PaymentDto target = queue.pollFirst(); // 배열 요소를 당기지 않고 Head 인덱스 번호만 +1 이동 (진짜 O(1))
    process(target);
}

```

* **면접 포인트**: `ArrayList`의 맨 뒤 삭제(`remove(size - 1)`)는 이동할 요소가 없어 **O(1)** 이지만, 맨 앞 삭제(`remove(0)`)는 전체 요소를 당겨와야 하므로 **O(N)** 이라는 극단적인 차이를 설명할 수 있어야 한다.

### 사례 2. `Arrays.asList()`와 `List.of()`를 일반 `ArrayList`로 착각해 발생한 런타임 예외와 원본 데이터 오염

현업 개발자들이 초기 데이터 세팅이나 테스트 코드를 작성할 때 `Arrays.asList()` 또는 `List.of()`로 리스트를 만든 뒤, 여기에 요소를 추가·수정하려다 운영 서버에서 런타임 에러(`UnsupportedOperationException`)를 터뜨리는 단골 실수이다.

```
// [실수 패턴 A: 크기 변경 시도로 인한 서버 에러]
List<String> roles = Arrays.asList("ROLE_USER", "ROLE_ADMIN");
if (isManager) {
    roles.add("ROLE_MANAGER"); // 💥 java.lang.UnsupportedOperationException 발생!
}

// [실수 패턴 B: 리스트를 수정했는데 원본 배열까지 몰래 바뀌는 버그]
String[] originalArray = {"A", "B", "C"};
List<String> wrapperList = Arrays.asList(originalArray);
wrapperList.set(0, "Z"); // wrapperList만 바꾼 줄 알았으나...
System.out.println(originalArray[0]); // 출력 결과: "Z" (원본 배열의 값까지 오염됨!)

```

#### ① 왜 이런 현상이 발생했는가? (내부 클래스 구조 해부)

개발자들은 `Arrays.asList()`가 우리가 흔히 쓰는 `java.util.ArrayList`를 만들어준다고 착각한다. 하지만 실제로는 이름이 같을 뿐 완전히 다른 **`java.util.Arrays$ArrayList`라는 내부 정적 클래스** 를 반환한다.

```
[일반 new ArrayList<>() vs Arrays.asList()의 메모리 구조 차이]

1. new ArrayList<>(Arrays.asList(originalArray))
   originalArray : [ "A" ][ "B" ][ "C" ]
   ArrayList     : [ "A" ][ "B" ][ "C" ][ 여유공간 ] (독립된 새 배열로 복사됨, 크기 확장 가능!)

2. Arrays.asList(originalArray)
   originalArray : [ "A" ][ "B" ][ "C" ]
                      ▲ (같은 배열 주소를 그대로 가리킴! 복사 안 함!)
   Arrays$ArrayList (껍데기만 List일 뿐, 알맹이는 크기 고정인 originalArray 그 자체!)

```

* **`Arrays.asList()`의 실체**: 새로운 배열을 만드는 게 아니라, **기존 정적 배열 위에 `List`라는 얇은 껍데기(View/Wrapper)만 씌운 것** 이다. 밑바닥 알맹이가 '크기 변경이 불가능한 정적 배열'이므로, 크기를 늘리는 `add()`나 줄이는 `remove()`를 호출하면 즉시 에러를 던진다. 게다가 원본 배열과 메모리를 공유하므로 한쪽을 고치면(`set`) 원본 배열도 같이 바뀐다.

* **`List.of()` (Java 9+)의 실체**: 아예 수정 자체가 완전히 금지된 **불변(Immutable) 리스트** 이다. `add()`, `remove()`는 물론이고 값을 바꾸는 `set()`을 호출해도 에러가 나며, 요소로 `null`을 넣는 것조차 허용하지 않는다(`NullPointerException` 발생).

| 구분 | `new ArrayList<>()` | `Arrays.asList()` | `List.of()` (Java 9+) | 
| ----- | ----- | ----- | ----- | 
| **실제 반환 클래스** | `java.util.ArrayList` | `java.util.Arrays$ArrayList` | `ImmutableCollections$ListN` | 
| **요소 추가/삭제 (`add`/`remove`)** | **가능** (동적 크기 확장) | **불가** (`UnsupportedOperationException`) | **불가** (`UnsupportedOperationException`) | 
| **요소 값 변경 (`set`)** | **가능** | **가능** (단, 원본 배열도 함께 변경됨) | **불가** (`UnsupportedOperationException`) | 
| **`null` 요소 허용 여부** | **허용** | **허용** | **불가** (`NullPointerException`) | 

#### ② 실무적 해결책

* 읽기 전용 상수로만 쓸 때는 `List.of()`를 쓰고, 이후 조건에 따라 요소를 추가하거나 삭제해야 한다면 반드시 **`new ArrayList<>()` 생성자로 한 번 감싸서 진짜 동적 배열로 복사본을 만들어야 한다**.

```
// 원본과 완전히 분리되고 크기 변경이 자유로운 진짜 ArrayList 생성
List<String> modifiableRoles = new ArrayList<>(List.of("ROLE_USER", "ROLE_ADMIN"));
modifiableRoles.add("ROLE_MANAGER"); // 정상 동작!

```

### 사례 3. `subList()`의 원본 참조 유지로 인한 500MB 메모리 누수(OOM)와 동시 수정 예외

대용량 로그 데이터 100만 건(약 500MB)을 메모리에서 정렬한 뒤, 상위 10건만 잘라내어(`subList(0, 10)`) 글로벌 캐시에 저장해 두는 기능을 구현했다가 서버 메모리가 터진 사례이다.

```
// [문제가 된 코드]
public List<Log> getTopTenRecentLogs() {
    // 1. 100만 건의 대용량 로그 리스트 생성 (약 500MB 차지)
    List<Log> largeLogs = logRepository.findMillionLogs(); 
    
    // 2. 상위 10건만 잘라서 반환 (개발자의 착각: "10개만 남고 999,990개는 GC가 치우겠지?")
    return largeLogs.subList(0, 10); 
}

```

#### ① 왜 이런 현상이 발생했는가? (`SubList` 내부 구조 해부)

많은 개발자가 `largeLogs.subList(0, 10)`을 호출하면 10개짜리 작은 배열이 새로 만들어져서 반환된다고 생각한다. 하지만 `ArrayList.subList()`는 **데이터를 전혀 복사하지 않는다**.

```
[largeLogs.subList(0, 10)의 실제 JVM Heap 메모리 구조]

 [글로벌 캐시] ──참조──> [ SubList 뷰 객체 ]
                         - root = largeLogs (원본 리스트의 주소값을 꽉 붙잡고 있음!)
                         - offset = 0
                         - size = 10
                              │
                              ▼ (GC가 절대 수거하지 못함!)
                    [ largeLogs 원본 내부 배열 (100만 건, 500MB) ]
                    [로그0][로그1]...[로그9] | [로그10] ... [로그999999 (더 이상 안 쓰는 99만9990개)]
                    <--- 내가 보는 10개 --->   <--- 함께 메모리에 감금된 500MB 덩어리 --->

```

1. **치명적인 메모리 누수 (Memory Leak)**: `subList()`가 반환하는 `ArrayList$SubList` 객체는 내부 필드로 **원본 리스트(`largeLogs`) 전체의 참조 주소(`root`)** 를 그대로 들고 있으면서, 단지 "0번부터 10개까지만 보여줘라"라는 눈가리개(창문) 역할만 한다. 따라서 이 10개짜리 `subList` 결과를 캐시나 전역 변수에 넣어두면, 가비지 컬렉터(GC)는 **"아직 원본 100만 건 리스트를 누군가 참조하고 있구나!"** 라고 판단하여 **500MB짜리 원본 배열 전체를 메모리에서 영원히 지우지 못한다**.

2. **`ConcurrentModificationException` 발생**: `subList`를 만든 상태에서 원본 `largeLogs`에 데이터를 하나라도 추가하거나 삭제한 뒤 `subList`를 조회하면, 원본 구조가 변했다는 것을 감지하고 즉시 `ConcurrentModificationException` 에러를 터뜨린다.

#### ② 실무적 해결책

* 큰 리스트에서 일부만 잘라내어 오래 보관하거나 외부로 반환할 때는, 원본 리스트와의 참조 사슬을 끊어내기 위해 **반드시 `new ArrayList<>(subList)`로 감싸서 10개만 담긴 독립된 새 배열로 복사** 해야 한다.

```
public List<Log> getTopTenRecentLogs() {
    List<Log> largeLogs = logRepository.findMillionLogs(); // 100만 건 (500MB)
    
    // 10개의 요소만 새로운 작은 배열로 복사하여 반환!
    // 메서드가 끝나는 순간 원본 largeLogs(500MB)는 참조가 끊어져 GC에 의해 즉시 메모리에서 회수됨!
    return new ArrayList<>(largeLogs.subList(0, 10)); 
}

```

## 3. Deep Dive: 밑바닥 동작 원리와 연쇄 의문 해부

### 3-1. 원시 타입 배열(`int[]`) vs 객체 동적 배열(`ArrayList<Integer>`)의 물리적 메모리 차이

같은 배열이라도 원시 타입(Primitive Type) 배열과 참조 타입(Reference Type) 동적 배열은 RAM과 CPU 캐시에서 동작하는 물리적 구조가 다르다.

```
[1] int[] 원시 타입 배열 (실제 4바이트 정수 '값' 자체가 물리 메모리에 연속 배치)
RAM 주소 : 0x1000      0x1004      0x1008      0x100C      ...  0x103C
데이터   : [ 100 ]     [ 200 ]     [ 300 ]     [ 400 ]     ...  [ 1600 ]
           arr[0]      arr[1]      arr[2]      arr[3]           arr[15]
           <----------- 64바이트 캐시 라인(Cache Line) 1개에 정수 16개 적재 ----------->

[2] ArrayList<Integer> 객체 동적 배열 (연속된 것은 실제 값이 아니라 4바이트 '참조 주소값')
내부 배열: 0x2000      0x2004      0x2008      0x200C
(Object[]) [ @0x5000 ] [ @0x7000 ] [ @0x9500 ] [ @0x3200 ] (참조 주소값들이 연속 배치됨)
                 │           │           │           │
                 ▼           ▼           ▼           ▼ (Pointer Dereference: 간접 참조 발생)
JVM Heap :   [Integer]   [Integer]   [Integer]   [Integer] (실제 객체들은 Heap 곳곳에 흩어져 있음)
             (값: 100)   (값: 200)   (값: 300)   (값: 400)

```

* **`int[]` (원시 배열)**: 메모리 공간에 4바이트 정수 값 자체가 빈틈없이 박혀 있다. `arr[0]`을 읽는 순간 64바이트 캐시 라인을 통해 `arr[0] ~ arr[15]`까지 16개의 실제 숫자 값이 L1 캐시에 한 번에 올라오며, 추가 참조 없이 즉시 연산된다.

* **`ArrayList<Integer>` (객체 동적 배열)**: 내부의 `Object[] elementData` 배열에 연속으로 들어있는 것은 실제 숫자가 아니라 Heap에 생성된 `Integer` 객체들을 가리키는 **4바이트 참조 주소값(Compressed OOPs 기준)** 이다. 참조 배열 자체는 연속되어 있어 `LinkedList`보다 훨씬 캐시 친화적이지만, 실제 값을 읽으려면 주소값을 타고 Heap의 `Integer` 객체로 한 번 더 점프(간접 참조)해야 하며 객체 헤더(12B) 등으로 인해 `int[]`보다 메모리를 약 4\~5배 더 소모한다.

### 3-2. 동적 배열의 크기 확장(Resize) 내부 의사코드와 분할 상환 분석

Java `ArrayList`에 요소를 추가할 때 내부에서 실행되는 핵심 로직을 의사코드로 표현하면 다음과 같다.

```
// Java ArrayList 내부의 add 및 grow(확장) 핵심 동작 원리
public boolean add(E e) {
    // 1. 현재 요소 개수(size)가 내부 배열 길이(elementData.length)와 같아졌는지 확인
    if (size == elementData.length) {
        elementData = grow(); // 공간이 꽉 찼다면 1.5배 확장된 새 배열로 교체!
    }
    // 2. 빈 공간에 바로 값 대입 후 size 1 증가 -> 평상시에는 단 1클럭 수준의 O(1)
    elementData[size] = e;
    size++;
    return true;
}

private Object[] grow() {
    int oldCapacity = elementData.length;
    // 비트 우측 시프트(>> 1)는 나누기 2와 같음. 즉, 기존 크기 + (기존 크기 * 0.5) = 1.5배 확장!
    int newCapacity = oldCapacity + (oldCapacity >> 1);
    
    // 새 배열을 Heap에 할당하고, OS/CPU의 고속 블록 복사(System.arraycopy)로 기존 데이터 이사 -> O(N) 소요
    return Arrays.copyOf(elementData, newCapacity);
}

```

#### 왜 1칸씩 늘리지 않고 1.5배(Java)나 2배(C++)로 늘리는가?

* 만약 공간이 모자랄 때마다 배열 크기를 **1칸씩만** 늘린다면, N개의 데이터를 넣을 때 복사 횟수는 `1 + 2 + 3 + ... + (N-1) = N(N-1)/2`가 되어 전체 시간 복잡도가 **O(N²)** 으로 추락한다.

* 반면 크기를 **2배씩(Doubling)** 늘린다고 가정하고 N개(예: 16개)를 넣으면, 복사는 크기가 1, 2, 4, 8일 때만 딱 4번 발생한다. 총 복사 횟수는 `1 + 2 + 4 + 8 = 15회 (< 2N)`이다.

* N번의 `add()`를 수행하는 동안 발생하는 총 연산 비용이 `N(단순 대입) + 2N(복사 비용) = 3N`이므로, 이를 N번의 작업으로 공평하게 나누면(분할 상환, Amortized) **1회 `add()`당 평균 비용은 약 3회 연산, 즉 O(1)** 이 된다.

### 3-3. 꼬리에 꼬리를 무는 의문 해결

#### 의문 1. "ArrayList와 LinkedList는 둘 다 중간 삽입/삭제 시간 복잡도가 O(N)인데, 왜 10만 건 리스트의 한가운데(5만 번째)에 값을 넣을 때 ArrayList가 훨씬 빠른가?"

같은 **O(N)** 이라도 하드웨어(CPU 캐시와 메모리 복사 방식)가 일하는 성격이 완전히 다르기 때문이다.

```
[10만 건 중 50,000번 인덱스에 요소를 삽입할 때의 실제 하드웨어 동작 비교]

1. LinkedList의 O(N) : "길을 찾는 데 O(N) + 연결 바꾸는 데 O(1)"
   [노드0] ──> [노드1] ──> [노드2] ... (Heap 메모리를 5만 번 점프하며 포인터 추적: Pointer Chasing!)
   - 다음 노드가 메모리 어디에 있는지 몰라 CPU 프리페치(미리 읽기)가 불가능함.
   - 캐시 미스가 연달아 터지며 RAM 접근 지연 시간이 수만 번 누적됨!

2. ArrayList의 O(N) : "위치 찾는 데 O(1) + 뒤쪽 5만 개를 밀어내는 데 O(N)"
   [참조0]...[참조50000][참조50001 ... 참조99999] ──(System.arraycopy)──> 옆 칸으로 한 번에 고속 복사!
   - 5만 번째 위치는 산술 계산으로 1클럭 만에 찾음 (O(1)).
   - 뒤쪽 5만 개의 참조값(약 200KB)을 밀어내는 작업은 연속된 메모리 블록을 옮기는 것이라,
     JVM 네이티브 레벨(C/어셈블리의 memmove, SIMD 벡터 명령어)에서 CPU 캐시 라인을 100% 타며 순식간에 끝남!

```

결과적으로 **불연속적인 메모리를 5만 번 점프하며 찾아가는 비용(`LinkedList`)** 보다, **연속된 메모리 블록 200KB를 CPU가 한 번에 긁어서 옆으로 밀어버리는 비용(`ArrayList`의 `System.arraycopy`)** 이 하드웨어 수준에서 수배에서 수십 배 더 빠르다.

#### 의문 2. "ArrayList가 꽉 찰 때마다 크기를 늘리고 복사하는 비용이 든다면, 코딩 테스트나 실무에서 미리 크기를 지정(`new ArrayList<>(N)`)해서 쓰는 게 유리한가?"

**매우 유리하며, 대량의 데이터를 다룰 때는 필수적인 최적화 습관이다**.

1. **코딩 테스트에서의 이점 (시간 초과 및 메모리 초과 방지)**:
   코딩 테스트에서 입력 데이터 N이 10만\~100만 개로 주어질 때 `new ArrayList<>()`를 기본 생성자로 쓰면, 데이터를 다 넣기까지 **약 25\~30번의 배열 재할당과 수백만 번의 `System.arraycopy` 복사 연산** 이 추가로 발생한다. 또한 마지막 확장 직후에는 실제 데이터 개수보다 최대 1.5배 큰 배열이 잡혀 있어 잉여 메모리를 낭비한다.
   반면 문제에서 주어진 N을 이용해 **`new ArrayList<>(N)`** 으로 생성하면:

   * 처음부터 정확히 N칸짜리 배열을 단 한 번만 할당하므로 **Resize 및 배열 복사 비용이 0회** 가 된다.

   * 불필요한 여유 공간(Slack Space) 없이 딱 필요한 만큼만 메모리를 쓴다.

   ```
   // [코딩 테스트 실전 팁: 그래프 인접 리스트 초기화 시]
   int N = 100000; // 정점 개수
   // 바깥쪽 리스트의 크기를 N + 1로 미리 지정하여 Resize 원천 차단!
   List<List<Integer>> graph = new ArrayList<>(N + 1);
   for (int i = 0; i <= N; i++) {
       graph.add(new ArrayList<>());
   }
   
   ```

2. **백엔드 실무에서의 이점 (Young GC 부하 감소)**:
   실무 API에서 DB 조회 결과 5만 건을 DTO 리스트로 변환할 때 초기 용량을 지정하지 않으면, 변환 과정에서 버려지는 십수 개의 중간 단계 배열 객체들이 JVM의 Eden 영역을 빠르게 채워 **불필요한 Minor GC(가비지 컬렉션)를 빈번하게 유발** 한다. 따라서 크기를 예측할 수 있는 컬렉션은 항상 초기 용량을 지정하는 것이 정석이다.

## 4. 핵심 요약 및 기술 면접 대비 (한국 IT 기업 기준)

### ① 개발 과정을 이해하기 위해 챙겨야 할 감각

* **연속성의 양날의 검 기억하기**: 배열의 연속 배치는 **O(1) 인덱스 조회와 극강의 CPU 캐시 효율** 이라는 선물을 주지만, 그 연속성을 유지하기 위해 **크기 확장(Resize)과 중간 삽입/삭제 시 데이터를 통째로 복사해 밀고 당겨야 하는 O(N)의 대가** 를 요구한다.

* **래퍼(Wrapper)와 뷰(View) 객체 의식하기**: `Arrays.asList()`나 `subList()`처럼 새로운 배열을 복사하지 않고 원본 배열의 참조만 공유하는 메서드들은, 잘못 쓰면 런타임 예외(`UnsupportedOperationException`)나 대형 메모리 누수(OOM)의 주범이 된다.

### ② 면접 모범 답변 스크립트

> **"배열은 동일한 크기의 데이터를 연속된 메모리 공간에 배치하여, 시작 주소와 인덱스를 이용한 산술 연산 한 번으로 O(1) 임의 접근이 가능하고 CPU 캐시 라인을 통한 공간 지역성 효율이 매우 뛰어난 자료구조입니다.**
>
> **정적 배열의 고정 크기 한계를 보완한 Java의 ArrayList는 내부 배열이 가득 차면 약 1.5배 크기의 새 배열을 할당해 System.arraycopy로 복사하는 방식으로 동작하며, 이를 통해 평균적으로 분할 상환 O(1)의 추가 성능을 보장합니다.**
>
> **다만 연속된 메모리 구조를 유지해야 하므로 중간이나 맨 앞 요소를 삽입·삭제할 때는 뒤쪽 요소를 전부 밀거나 당기는 O(N)의 복사 비용이 발생합니다. 따라서 실무에서는 조회 및 순차 추가에는 초기 용량을 지정한 ArrayList를 기본으로 사용하되, 맨 앞 요소의 삽입·삭제가 빈번한 큐 작업에서는 원형 배열 기반의 ArrayDeque를 선택해 최적화합니다."**

| **초기 용량(`initialCapacity`) 지정과 GC 영향** | ★★★★☆ | **실무 최적화 질문** | 대용량 데이터를 다룰 때 왜 `new ArrayList<>(size)`를 써야 하는지, 미지정 시 발생하는 불필요한 배열 복사와 Young 영역 GC 오버헤드를 연결해 답할 수 있는지 본다. | 
| **`Arrays.asList()`, `List.of()`, `subList()` 주의점** | ★★★☆☆ | **Java 실무 경험 검증 질문** | 실무에서 Java 컬렉션을 깊게 다뤄봤는지 확인하는 질문이다. 특히 `subList()`의 원본 참조 유지로 인한 메모리 누수(OOM) 사례를 언급하면 실무 감각에서 큰 가산점을 받는다. |
