# [CS] 컴퓨터가 정보를 이해하는 법 (0과 1의 세계: 비트, 2의 보수, 부동소수점, 문자 인코딩)

## 0. 시스템 버스 위를 달리는 것의 실체와 인코딩(Encoding)

디스크에 있던 프로그램이 RAM에 올라가고, CPU가 시스템 버스를 통해 명령어를 가져와 실행한다. 그렇다면 CPU와 RAM을 잇는 구리 전선(시스템 버스) 위를 실제로 달리는 것은 무엇일까? 진짜 `'ADD'` 같은 명령어나 `'apple'` 같은 문자열이 날아다니는 것이 아니라, 실제로는 오직 **전압(전기 신호)** 만 흐른다.

이때 전압이 약하게 흐른다거나 강하게 흐른다로 구분하지 않고, 오직 **"전기가 흐르는가(On), 흐르지 않는가(Off)"** 두 가지 상태로만 구분한다. 전압 세기를 세밀하게 나누면 노이즈(잡음) 때문에 데이터가 오염되기 쉽지만, 켜짐과 꺼짐 두 가지로만 나누면 물리적 오류가 거의 발생하지 않기 때문이다. 컴퓨터는 이 두 가지 상태를 **1과 0**, 즉 **비트(Bit)** 라는 정보의 최소 단위로 정의했다.

### 💡 의문: 1과 0밖에 없는데 어떻게 복잡한 문자와 숫자를 표현할까?

정답은 **인코딩(Encoding, 부호화)** 이다.

* **인코딩(Encoding)**: 인간이 사용하는 문자, 숫자, 기호 등의 정보를 컴퓨터가 처리할 수 있는 **0과 1의 이진수(비트 열)로 변환하는 표준 규칙(약속)** 이다. (반대로 0과 1을 인간의 문자로 되돌리는 것은 **디코딩** 이라 한다.)
* 0과 1이라는 전기 스위치를 몇 개씩 묶어서 어떤 데이터로 해석할지 하드웨어 설계자들이 국제 표준 규약을 맺어두었기 때문에, 컴퓨터는 0과 1만으로 모든 정보를 오차 없이 다룰 수 있다.

## 1. 비트(Bit)와 바이트(Byte), 그리고 메모리 번지(Address)

* **비트 (Bit)**: 0과 1을 담는 정보의 **최소 단위** 이다.
* **바이트 (Byte)**: 비트 8개를 하나로 묶은 단위(`1 Byte = 8 bits`)이며, **컴퓨터가 메모리 주소(Address)를 할당하는 최소 단위** 이다.

### 💡 의문: 왜 1비트마다 주소를 주지 않고 8비트(1바이트)씩 묶어서 주소를 줄까?

비유하자면 아파트 우편물을 보낼 때 **'101호, 102호(집 단위 = 1바이트)'** 에 주소를 부여하지, 집 안의 **'화장실 바닥 타일 1번, 2번(1비트)'** 마다 고유 우편번호를 붙이지 않는 것과 같다.

1. **주소 관리 비용 폭증**: 1비트마다 고유 주소 번지(`0x00`, `0x01`...)를 매기면, 16GB RAM의 모든 비트를 가리키기 위해 주소 버스(Address Bus) 전선 개수와 주소를 담는 포인터 크기가 8배로 커져야 한다.
2. **데이터 표현의 경제성**: 1비트로는 참/거짓밖에 표현할 수 없다. 영문자 1글자나 기본 제어 명령을 표현하기에 가장 알맞은 크기가 8비트($2^8 = 256$가지 상태)였기 때문에, 하드웨어는 회로를 설계할 때부터 **8비트(1바이트) 묶음마다 주소 번지를 하나씩 붙이도록 물리적으로 고정(Hard-wired)** 해 두었다.

## 2. 정수와 음수의 표현: 2의 보수 (Two's Complement)

CPU 내부의 산술논리연산장치(ALU)에는 덧셈을 수행하는 **가산기(Adder)** 회로가 들어있다. 만약 뺄셈을 위해 별도의 '감산기' 회로를 따로 설계하면 CPU 칩 내부 면적이 낭비되고 발열과 제조 비용이 증가한다.

그래서 공학자들은 **"어떤 수를 음수로 만들어서 덧셈기에 넣었을 때, 자연스럽게 뺄셈 결과가 나오도록 음수를 정의할 수는 없을까?"** 를 고민했고, 그렇게 고안된 것이 **2의 보수** 이다.

### 2의 보수 변환과 덧셈을 통한 뺄셈 과정 (`5 - 5` 계산 예시)

1. **양수 5의 표현**: `0000 0101`
2. **음수 -5 만들기 (2의 보수)**:
   * 모든 비트를 반전시킨다: `1111 1010` (여기까지가 **1의 보수** 이다)
   * 여기에 `1`을 더한다: `1111 1011` (이것이 **-5의 2의 보수 표현** 이다)
3. **ALU에서 `5 + (-5)` 연산 수행**:

```text
    0000 0101  ( 5 )
  + 1111 1011  (-5, 2의 보수)
  --------------------------
(1) 0000 0000  --> 8비트 범위를 넘어간 올림수(Carry) 1비트는 버림 = 결과: 0
```

이처럼 2의 보수를 사용하면 감산기 없이 **덧셈 회로 하나로 뺄셈까지 완벽하게 처리** 할 수 있다. 또한 1의 보수와 달리 `+0`과 `-0`이 중복되지 않고 유일한 `0`(`0000 0000`)만 존재한다는 장점이 있다.

### 💡 의문: 덧셈과 뺄셈은 알겠는데, 곱셈과 나눗셈은 어떻게 처리할까?

곱셈과 나눗셈 역시 **비트 이동(Shift)과 덧셈/뺄셈의 반복** 으로 처리한다.

* **곱셈**: 10진수에서 $10$을 곱할 때 자릿수를 왼쪽으로 한 칸 밀어 `0`을 붙이듯, 2진수에서도 비트를 왼쪽으로 한 칸 밀면(`<< 1`) 곱하기 $2$가 된다. 예를 들어 $5 \times 3$은 $5 \times (2 + 1)$이므로, `5를 왼쪽으로 1칸 시프트한 값(10)`과 `5`를 덧셈기로 더해서 결과를 낸다.
* **나눗셈**: 반대로 비트를 오른쪽으로 밀면서(`>>`) 2의 보수를 이용한 뺄셈을 반복하여 몫과 나머지를 구한다. (현대 CPU는 속도를 높이기 위해 시프트와 가산기를 다단으로 묶은 고속 승산기/제산기 회로를 내장하고 있다.)

## 3. 실수의 표현: 부동소수점 (IEEE 754 Floating Point)

컴퓨터에서 `0.1`이나 `3.14` 같은 실수를 저장할 때는 소수점의 위치를 고정하지 않고 둥둥 떠다니게 만드는 **부동소수점(Floating Point)** 방식을 사용한다.

32비트 실수(`float`)는 메모리에 다음과 같이 분할되어 기록된다.

```text
 1 bit     8 bits                     23 bits
+------+------------+-------------------------------------------------+
| 부호 |  지수부    |                    가수부                       |
| Sign |  Exponent  |                   Fraction                      |
+------+------------+-------------------------------------------------+
```

* **부호 비트 (1 bit)**: `0`이면 양수, `1`이면 음수이다.
* **지수부 (8 bits)**: 소수점의 위치를 이동시키는 $2^n$ 거듭제곱 승수이다.
* **가수부 (23 bits)**: 실제 정밀한 유효 숫자 비트들을 담는다. (64비트 `double`은 가수부가 52비트이다.)

### 💡 의문: 왜 소수점이 '둥둥 떠다닌다(부동, Floating)'고 표현할까?

8칸짜리 숫자판이 있다고 가정해 보자. 만약 뒤의 2칸을 소수점 자리로 고정(**고정소수점**)하면 `123456.78`처럼 큰 수는 못 넣고, `0.000012`처럼 아주 작은 수도 표현하지 못한다.

반면 실수를 **$1.2345 \times 10^5$ (과학적 표기법)** 형태로 바꾸면 어떨까?

* **가수부** 에는 핵심 유효 숫자인 `12345`만 저장한다.
* **지수부** 에 넣는 숫자($10^5$, $10^{-3}$ 등)에 따라 소수점의 위치가 `123450.0`이 되기도 하고 `0.0012345`가 되기도 한다.
* 즉, **지수부의 값에 따라 소수점의 위치가 고정되지 않고 좌우로 자유롭게 이동(Floating)** 하기 때문에 부동소수점이라 부르며, 덕분에 적은 비트 수로도 엄청나게 넓고 정밀한 범위의 실수를 표현할 수 있다.

### 부동소수점의 치명적 한계와 10진 임의정밀도 (`BigDecimal`)

부동소수점에는 치명적인 약점이 있다. 10진수 `0.1`을 2진수로 변환하면 다음과 같이 끝없이 반복되는 **무한 순환 소수** 가 된다.
$$0.1_{(10)} = 0.000110011001100110011..._{(2)}$$

컴퓨터의 가수부 공간은 23비트(또는 52비트)로 한정되어 있으므로, 무한히 이어지는 비트의 뒷부분을 강제로 잘라내어 저장한다. 이로 인해 **필연적인 미세한 소수점 근사 오차(Round-off Error)** 가 발생한다.

따라서 단 1원의 오차도 허용되지 않는 금융, 결제, 회계 시스템에서는 부동소수점 대신 **10진 임의정밀도(`BigDecimal`)** 방식을 사용한다.

* **10진 임의정밀도의 원리 (예시)**: `12.34`라는 실수를 2진 소수로 바꾸지 않고, **정수 값(`1234`)** 과 **소수점 이하 자릿수(`scale = 2`)** 라는 두 개의 정수로 분리해 저장한다. 계산할 때도 $1234 \times 10^{-2}$처럼 10진수 정수 연산을 수행하므로 2진수 변환 오차가 아예 발생하지 않는다.

| 비교 항목 | 부동소수점 (`float`, `double`) | 10진 임의정밀도 (`BigDecimal`) |
| :--- | :--- | :--- |
| **저장 원리** | 2진수 기반 지수부 + 가수부 분할 저장 | 10진수 기반 **정수 배열 + 소수점 위치(Scale)** 저장 |
| **정확도** | **미세한 근사 오차 발생** (`0.1 + 0.2 != 0.3`) | **오차 제로** (인간의 10진수 계산과 100% 일치) |
| **연산 속도** | **초고속** (CPU 내부의 FPU 하드웨어가 직접 계산) | **느림** (소프트웨어 객체로 자릿수를 일일이 계산) |
| **주요 용도** | 게임 물리 엔진, 3D 그래픽스, AI 연산 | **금융, 이커머스 결제, 정산, 화폐 계산** |

## 4. 문자의 표현: ASCII에서 유니코드(UTF-8)까지

컴퓨터는 문자를 직접 이해하지 못하므로, **특정 숫자 번호(코드 포인트)에 특정 글자를 1:1로 대응시키는 문자 표** 를 보고 문자를2진수로 변환한다.

```text
[문자 'A'] ---> 아스키/유니코드 매핑 ---> 십진수 65 (0x41)   ---> 1바이트: 0100 0001
[문자 '가'] ---> UTF-8 가변 인코딩   ---> 0xEA, 0xB0, 0x80 ---> 3바이트(24비트) 저장
```

* **ASCII (아스키, 7/8비트)**: 미국 표준 문자셋이다. 영문 알파벳, 숫자, 특수기호 등 128개($2^7$)의 문자만 표현할 수 있으며 한글이나 한자는 표현이 불가능하다.
* **유니코드 (Unicode)**: 전 세계 모든 나라의 언어와 이모지(Emoji)를 하나의 체계에 담기 위해 각 글자마다 고유 번호(예: `'A'`는 `U+0041`, `'가'`는 `U+AC00`)를 부여한 국제 표준이다.
* **UTF-8 (가변 길이 인코딩)**: 유니코드 번호를 실제 컴퓨터 메모리에 저장할 때 바이트 낭비를 막기 위해 고안된 방식이다. 글자 종류에 따라 **1바이트에서 4바이트까지 크기를 다르게** 저장한다.
  * **영문자 / 숫자 / 기본 기호**: **1바이트** (기존 ASCII와 100% 호환되며 메모리 낭비가 없다.)
  * **한글 / 한자 / 일본어**: **3바이트** (초성·중성·종성이 결합된 현대 한글 1글자는 UTF-8에서 무조건 **3바이트** 를 차지한다.)
  * **이모지 (😀, 🔥 등)**: **4바이트**

## 5. 실무 개발 '아하(Aha!)' 모먼트 연결

### 사례 1: "결제 할인율 계산 코드를 짰는데, 정산 장부에서 돈이 안 맞는다!"

```java
double discountRate = 0.9; // 10% 할인
double result = 1.0 - discountRate; // 0.1을 기대함

System.out.println(result); // 실제 출력: 0.09999999999999998
if (result == 0.1) {
    System.out.println("정상 처리");
} else {
    System.out.println("할인 누락 버그 발생!"); // <--- 여기가 실행된다!
}
```

* **원인**: CPU는 `0.1`을 IEEE 754 부동소수점 2진수로 정확히 표현하지 못하고 가장 가까운 근사치로 저장한다. 따라서 실수 비교에 `==`을 쓰면 버그가 터지고, 수만 건의 결제 금액을 `double`로 합산하면 오차가 누적되어 실제 돈이 비는 사고가 난다.
* **해결책**: 금액, 할인율, 정산 로직에서는 절대 `double`이나 `float`을 쓰지 말고 반드시 **`BigDecimal`** 을 사용하거나, 정수형(`long`) 단위로 변환해 계산해야 한다.

### 사례 2: "분명 10글자 제한 컬럼인데, 한글 4글자를 넣었더니 DB 에러가 터진다!"

* **상황**: DB에 `VARCHAR(10)` 컬럼을 만들었다. 영어 아이디 `"abcdefghij"`(10자)는 잘 들어가는데, 한글 닉네임 `"홍길동입니다"`(6자)를 넣자 `Data too long` 에러가 발생한다.
* **원인**: UTF-8 인코딩에서 영어는 1글자가 **1바이트** 지만, 한글은 1글자가 **3바이트** 이다. DB 설정이 '10글자'가 아닌 **'10바이트'** 기준으로 되어 있다면 한글은 3글자(`9바이트`)까지만 들어가고 4글자(`12바이트`)부터는 용량 초과로 튕겨 나간다. (또한 이모지 4바이트를 저장하려면 MySQL에서는 기본 `utf8`이 아닌 `utf8mb4` 설정을 써야 한다.)

### 사례 3: "조회수가 21억 회를 넘자마자 갑자기 마이너스(-21억)로 변했다!"

* **원인 (정수 오버플로우)**: 32비트 부호 있는 정수(`int`)는 맨 앞 1비트를 부호(0: 양수, 1: 음수)로 쓴다. 표현 가능한 최대 양수는 `0111 1111 ...` 즉 약 21억 4천만($2^{31} - 1$)이다. 여기에 `1`을 더하는 순간 비트가 `1000 0000 ...`으로 넘어가며, 2의 보수 규칙에 의해 **가장 작은 음수(-21억 4천만)** 로 뒤집히는 오버플로우(Overflow) 현상이 발생한다. 누적 조회수나 주문 번호(PK)는 반드시 64비트 정수인 **`long`(`BIGINT`)** 으로 설계해야 한다.

### 🎯 면접을 위해 머릿속에 남겨야 할 핵심 질문 2가지

1. **"컴퓨터는 왜 뺄셈을 할 때 별도의 감산기를 쓰지 않고 2의 보수를 사용하나요?"**
   * **핵심 답변**: 하드웨어 회로 설계 시 덧셈기(가산기) 외에 별도의 감산기 회로를 추가하면 CPU 칩 면적과 비용이 늘어나기 때문이다. 음수를 2의 보수(비트 반전 후 +1)로 표현하면, 덧셈기 회로에 그대로 넣었을 때 최상위 올림수만 버리는 것만으로 뺄셈 연산이 완벽하게 수행된다.
2. **"자바에서 `double`이나 `float`을 결제/정산 시스템에 사용하면 안 되는 이유는 무엇인가요?"**
   * **핵심 답변**: `double`과 `float`은 IEEE 754 부동소수점 방식을 사용하는데, 10진수 `0.1` 같은 소수를 2진수로 변환하면 무한 순환 소수가 된다. 한정된 가수부 비트에 이를 잘라서 저장하므로 미세한 근사 오차가 발생할 수밖에 없다. 따라서 금융/결제 로직에서는 속도가 조금 느리더라도 10진수 정수와 스케일 기반으로 오차 없이 계산하는 `BigDecimal`을 사용해야 한다.
