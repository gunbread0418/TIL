# CPU의 구조와 명령어 사이클

메모리(RAM)는 단지 데이터를 보관하기만 하는 수동적인 저장소일 뿐이다. 예를 들어 메모리에 `0100 0001`이라는 비트가 들어있을 때, 이를 문자 `'A'`로 화면에 출력할지, 숫자 `65`로 덧셈 연산을 할지, 아니면 특정 기계어 명령어로 실행할지 결정하고 실제로 작업을 밀어붙이는 능동적인 주체가 필요하다. 그 주체가 바로 **CPU (Central Processing Unit, 중앙처리장치)** 이다.

---

## 1. CPU 내부의 핵심 구성 요소

CPU 칩 내부는 크게 산술/논리 연산을 수행하는 장치, 명령어를 해석하고 지시하는 장치, 그리고 데이터를 초고속으로 임시 저장하는 여러 레지스터들로 이루어져 있다.

### ① ALU (산술논리연산장치, Arithmetic Logic Unit)
* CPU 내부에서 실제 계산을 전담하는 하드웨어 회로다.
* 덧셈, 뺄셈 같은 산술 연산과 AND, OR, NOT, 크기 비교 같은 논리 연산을 물리적인 전기 신호로 수행한다.
* 연산을 마친 직후에는 그 결과의 상태(연산 결과가 0인지, 음수인지, 자리올림이나 오버플로우가 발생했는지 등)를 **플래그 레지스터 (Flag Register)** 에 기록하여 다음 명령어가 참고할 수 있게 한다.

### ② CU (제어장치, Control Unit)
* CPU의 두뇌 역할을 하는 지휘 본부다.
* 메모리에서 가져온 기계어 명령어 비트를 해독(Decode)하고, 그 의미에 맞게 CPU 내부의 ALU, 레지스터, 그리고 외부의 메모리와 입출력 장치들에게 제어 버스를 통해 전기적인 제어 신호(예: "메모리를 읽어라", "덧셈 회로를 가동해라")를 내보낸다.

### ③ 레지스터 (Registers)
CPU 내부에 존재하는 가장 빠른 초소형 임시 저장 공간이다. 용도에 따라 각각의 역할이 엄격히 나뉘어 있다.
* **PC (프로그램 카운터, Program Counter)** : CPU가 **다음에 실행할 명령어가 저장된 메모리의 주소(번지)** 를 가리키는 레지스터다. 특별한 분기문(`if`, `for`, 함수 호출)이 없는 한 명령어를 하나 인출할 때마다 자동으로 다음 명령어 주소로 증가한다.
* **MAR (메모리 주소 레지스터, Memory Address Register)** : CPU가 메모리의 특정 번지를 읽거나 쓰려고 할 때, PC가 가리키는 주소값을 시스템의 **주소 버스(Address Bus)** 로 내보내기 직전에 임시로 담아두는 창구 역할의 레지스터다.
* **MBR (메모리 버퍼 레지스터, Memory Buffer Register / MDR)** : 메모리에서 읽어온 데이터나 명령어가 CPU로 들어올 때, 혹은 CPU에서 계산된 값을 메모리로 내보낼 때 **데이터 버스(Data Bus)** 와 맞닿아 데이터를 임시로 주고받는 버퍼 레지스터다.
* **IR (명령어 레지스터, Instruction Register)** : 메모리에서 방금 읽어와 MBR에 도착한 데이터 중 **현재 당장 실행해야 할 기계어 명령어** 를 넘겨받아 보관하는 레지스터다. 제어장치(CU)는 이 IR에 담긴 비트를 읽어서 명령을 해석한다.
* **범용 레지스터 (General Purpose Registers)** : `AX`, `BX`, `CX`, `DX` (64비트에서는 `RAX`, `RBX` 등)처럼 연산에 필요한 피연산자 데이터나 연산 중간 결괏값을 자유롭게 담아두는 작업 공간이다.

## 2. CPU와 메인 메모리(RAM)의 상호작용 구조

CPU 내부의 유닛들과 메인 메모리가 3대 시스템 버스(제어, 주소, 데이터 버스)를 통해 연결되어 상호작용하는 전체 구조는 다음과 같다.

```text
+-----------------------------------------------------------------------------------------+
|                                        C P U                                            |
|                                                                                         |
|  +--------------------+                     +----------------------------------------+  |
|  |  제어장치 (CU)     |<---[기계어 코드]----+  명령어 레지스터 (IR)                  |  |
|  |  (Control Unit)    |                     |  - 현재 실행 중인 명령어를 임시 보관   |  |
|  |                    |                     +----------------------------------------+  |
|  |  - 명령어 디코딩   |                                                                 |
|  |  - 하드웨어 제어선 |                     +----------------------------------------+  |
|  +---------+----------+                     |  프로그램 카운터 (PC)                  |  |
|            |                                |  - 다음에 실행할 메모리 번지 보관      |  |
|            | (제어 신호)                    +-------------------+--------------------+  |
|            v                                                    | (주소 전달)           |
|  +--------------------+                     +-------------------v--------------------+  |
|  |  연산장치 (ALU)    |                     |  메모리 주소 레지스터 (MAR)            |  |
|  |  - 산술/논리 연산  |                     |  - 주소 버스로 나갈 번지 보관          |  |
|  |  - 플래그 레지스터 |                     +-------------------+--------------------+  |
|  +---------^----------+                                         |                       |
|            | (피연산자 데이터)                                  |                       |
|  +---------v---------------------------+    +-------------------v--------------------+  |
|  |  범용 레지스터군 (AX, BX, CX, DX 등)|<-->|  메모리 버퍼 레지스터 (MBR / MDR)      |  |
|  |  - 연산 데이터 임시 저장            |    |  - 데이터 버스로 오가는 값 임시 보관   |  |
|  +-------------------------------------+    +-------------------+--------------------+  |
+-----------------------------------------------------------------|-----------------------+
                                                                  |
 ================================== 시스템 버스 ==================|=========================
   제어 버스 (Control Bus)   <--- CU의 MEMORY READ/WRITE 신호 -----+
   주소 버스 (Address Bus)   <--- MAR의 메모리 주소 신호
   데이터 버스 (Data Bus)    <---> MBR의 0과 1 데이터 비트
 =================================================================|=========================
                                                                  v
                                                     +------------------------+
                                                     |    메인 메모리 (RAM)    |
                                                     |  0x1000: [ ADD AX, BX ]|
                                                     +------------------------+
```

## 3. 명령어 사이클 (Instruction Cycle) 4단계 상세 추적

프로그램이 실행된다는 것은 결국 CPU가 메모리에 올라와 있는 기계어 명령어들을 하나씩 가져와 실행하는 과정을 수십억 번 반복하는 것이다. 이 하나의 명령어를 처리하는 정형화된 주기를 **명령어 사이클** 이라고 한다.

메모리 `0x1000` 번지에 `ADD AX, BX` ("AX 레지스터의 값과 BX 레지스터의 값을 더해서 다시 AX 레지스터에 저장하라"는 32비트/4바이트 길이의 명령어)가 들어있다고 가정했을 때, CPU 내부에서 벌어지는 물리적 4단계 과정은 다음과 같다.

### [1단계: 인출 사이클 (Fetch Cycle)] — 메모리에서 명령어를 CPU로 가져오기
아직 CPU는 자신이 무슨 연산을 해야 하는지 모른다. 우선 메모리에 있는 명령어를 CPU 내부로 가져와야 한다.
1. **PC 확인 및 주소 전달 (`PC -> MAR`)** : 현재 PC 레지스터에는 다음에 실행할 명령어의 위치인 `0x1000`이 들어있다. CPU는 이 주소를 주소 버스로 내보내기 위해 먼저 **MAR(메모리 주소 레지스터)** 로 복사한다.
2. **버스 신호 전송** : MAR에 담긴 `0x1000` 번지 신호가 **주소 버스** 를 타고 RAM으로 전달된다. 동시에 제어장치(CU)는 **제어 버스** 를 통해 RAM에게 `"해당 번지의 데이터를 읽어라 (MEMORY READ)"`라는 전기 신호를 보낸다.
3. **데이터 버스 탑승 (`RAM -> MBR`)** : RAM의 메모리 컨트롤러는 `0x1000` 번지에 저장된 `ADD AX, BX`에 해당하는 0과 1의 기계어 비트열을 꺼내어 **데이터 버스** 에 실어 보낸다. 이 비트열은 CPU의 관문인 **MBR(메모리 버퍼 레지스터)** 에 도착해 담긴다.
4. **명령어 등록 및 PC 증가 (`MBR -> IR`, `PC + 4`)** : MBR에 도착한 데이터는 지금 실행해야 할 명령어이므로 **IR(명령어 레지스터)** 로 옮겨진다. 이와 동시에 **PC(프로그램 카운터)** 의 값은 다음 명령어를 가리키기 위해 명령어 크기(4바이트)만큼 증가하여 자동으로 `0x1004`가 된다. (이 덕분에 프로그램이 위에서 아래로 순차 실행된다.)

### [2단계: 해석 사이클 (Decode Cycle)] — 가져온 명령어가 무슨 뜻인지 분석하기
1. **비트의 분할 판독 (`IR -> CU`)** : 명령어는 크게 **연산 코드(Opcode: 무엇을 할 것인가)** 와 **오퍼랜드(Operand: 누구를 대상으로 할 것인가)** 두 부분의 비트로 나뉘어 있다.
2. **디코딩 및 제어선 활성화** : 제어장치(CU) 내부의 디코더 회로가 IR의 비트 패턴을 해독한다. 그 결과 "앞쪽 비트는 덧셈(`ADD`)을 뜻하고, 뒤쪽 비트는 범용 레지스터 `AX`와 `BX`를 뜻한다"는 사실을 파악하고, 다음 단계에 필요한 하드웨어 회로들의 스위치를 켤 준비를 마친다.

### [3단계: 실행 사이클 (Execute Cycle)] — 실제로 계산을 수행하기
1. **ALU 제어 신호 인가** : 제어장치(CU)가 연산장치(ALU)에게 덧셈 회로를 활성화하라는 제어 신호를 보낸다. 또한 범용 레지스터 `AX`와 `BX`의 출력 문을 열어 그 안에 들어있던 숫자 데이터가 ALU의 입력단으로 흘러 들어가게 한다.
2. **산술 연산 및 플래그 갱신** : ALU 내부의 가산기(Adder) 회로를 통과하며 두 값이 전기적으로 더해진다. 이때 연산 결과가 0인지, 음수인지, 혹은 표현 범위를 넘어선 오버플로우(Overflow)가 발생했는지 여부가 **플래그 레지스터** 에 함께 기록된다.

### [4단계: 기록 사이클 (Write-back / Store Cycle)] — 연산 결과를 저장하기
1. **목적지 저장** : ALU의 출력단으로 나온 덧셈 결괏값을 명령어가 지정한 최종 목적지인 **범용 레지스터 `AX`** 에 덮어쓴다. (만약 결과를 메모리에 저장하라는 명령어였다면, 다시 MBR과 데이터 버스를 거쳐 RAM에 기록한다.)
2. 이 4단계가 끝나면 CPU는 지체 없이 다시 1단계(Fetch)로 돌아가, 아까 `0x1004`로 증가해 둔 **PC** 값을 보고 그다음 명령어를 가져오며 사이클을 무한 반복한다.

## 4. 클럭(Clock), 코어(Core), 그리고 스레드(Thread)의 본질

### ① 클럭 (Clock, GHz)
* CPU 내부의 부품들이 한 박자에 맞춰 일사불란하게 움직이도록 석영 진동자(크리스탈)가 일정한 주기로 만들어내는 **전기적 펄스(맥박) 신호** 다.
* CPU 내부의 모든 레지스터와 논리 회로는 클럭 신호가 0에서 1로 튀어 오르는 순간(Rising Edge)에 맞춰 데이터를 다음 단계로 이동시킨다.
* 예를 들어 `3.0 GHz`라는 사양은 1초에 30억 번($3 \times 10^9$)의 전기적 진동이 발생한다는 뜻이다. 클럭 속도가 높을수록 1초 동안 수행할 수 있는 명령어 사이클의 횟수가 많아져 연산 속도가 빨라지지만, 그만큼 소비 전력과 발열이 급격히 증가한다.

### ② 코어 (Core)
* 과거에는 CPU 칩 하나가 곧 하나의 두뇌였지만, 클럭 주파수를 무작정 높이다 보니 칩이 열을 견디지 못하고 녹아내리는 **발열 장벽(Power Wall)** 에 부딪혔다.
* 이를 극복하기 위해 클럭을 무리하게 올리는 대신, CPU 칩 하나 안에 **독립적으로 명령어 사이클(인출-해석-실행-기록)을 돌릴 수 있는 물리적 CPU 두뇌 세트(ALU + CU + 레지스터군 + L1/L2 캐시)** 를 여러 개 집어넣는 방식으로 진화했다. 이 독립된 물리적 두뇌 1세트를 **코어(Core)** 라고 부르며, 코어가 4개면 쿼드코어, 8개면 옥타코어라고 한다.

### ③ 하드웨어 스레드(하이퍼스레딩) vs 소프트웨어 스레드 비교
공부를 하다 보면 CPU 사양에서 말하는 **"8코어 16스레드(하이퍼스레딩)"** 와 프로그래밍(Java, OS)에서 말하는 **"멀티스레드"** 가 둘 다 '스레드'라는 단어를 써서 헷갈리기 쉽다. 이 둘은 층위가 다른 개념이다.

* **일반적인 스레드 (소프트웨어 스레드 / OS 스레드)** :
  * 운영체제(OS)가 프로그램(프로세스) 안에서 실행 흐름을 여러 갈래로 나누기 위해 만든 **논리적인 작업 단위** 다. 개발자가 코드에서 `new Thread()`로 500개를 만들든 1,000개를 만들든 메모리가 허용하는 한 얼마든지 생성할 수 있다.
* **하이퍼스레딩 (하드웨어 스레드 / 논리 코어)** :
  * 물리 코어 1개 안에는 ALU(연산장치)가 들어있는데, CPU가 느린 RAM에서 데이터를 가져오는 수십 나노초 동안 이 비싼 ALU가 아무 일도 못 하고 멍하니 노는 유휴 시간(Stall)이 발생한다.
  * 인텔(Intel)이나 AMD 같은 하드웨어 제조사는 이 노는 시간이 아까워서, **물리 코어(ALU)는 1개만 두되 그 코어 안에 있는 레지스터 세트(PC, IR, 범용 레지스터 등)만 2쌍으로 복제** 해 두었다.
  * 이렇게 하면 1번 레지스터 세트가 메모리에서 데이터를 기다리며 멈춰 있을 때, 코어 안의 ALU가 놀지 않고 즉시 2번 레지스터 세트의 명령어를 대신 계산할 수 있다. 운영체제(OS) 입장에서는 레지스터 세트가 2개이니 마치 물리 코어가 2개인 것처럼 인식하게 되는데, 이를 **하이퍼스레딩(Hyper-Threading)** 또는 **논리 프로세서(하드웨어 스레드)** 라고 부른다.

## 5. CPU 설계 철학의 양대 산맥: CISC vs RISC

CPU가 어떤 규격의 기계어 명령어를 해석하고 실행하도록 설계할 것인가(ISA, 명령어 집합 구조)에 따라 현대 프로세서는 크게 **CISC** 와 **RISC** 두 진영으로 나뉜다. 이는 오늘날 PC/서버용 Intel·AMD 칩과 모바일/Mac용 ARM(Apple Silicon) 칩의 근본적인 차이를 만든 뿌리다.

### 💡 표를 보기 전에 이해해야 할 핵심: '가변 길이 명령어' vs '고정 길이 명령어'란?

메모리에는 수많은 기계어 명령어 비트들이 빈틈없이 일렬로 나열되어 있다. 이때 각 명령어 하나가 차지하는 바이트 크기를 어떻게 정하느냐의 차이다.

```text
[CISC의 가변 길이 명령어] -> 명령어마다 크기가 1바이트~15바이트로 제각각임
+--------+-----------------------+--------------+-------------------------------+
| 명령어1 |        명령어2         |    명령어3    |             명령어4            |
| (1Byte)|        (6Byte)        |    (3Byte)   |             (10Byte)          |
+--------+-----------------------+--------------+-------------------------------+
-> 문제점: CPU 제어장치(CU)가 명령어1을 읽은 뒤, "명령어2가 어디서부터 어디까지인지" 
          해독하기 전에는 알 수가 없다. 회로가 매우 복잡해지고 파이프라인 병렬 처리가 어렵다.

[RISC의 고정 길이 명령어] -> 모든 명령어의 크기가 무조건 4바이트(32비트)로 똑같음
+----------------+----------------+----------------+----------------+
|     명령어1     |     명령어2     |     명령어3     |     명령어4     |
|    (4Byte)     |    (4Byte)     |    (4Byte)     |    (4Byte)     |
+----------------+----------------+----------------+----------------+
-> 장점: 모든 명령어가 자로 잰 듯 4바이트씩 떨어져 있으므로, 제어장치(CU)가 고민할 필요 없이 
        무조건 4바이트 단위로 끊어서 초고속으로 읽고 동시에 여러 명령어를 겹쳐서(파이프라이닝) 처리할 수 있다.
```

* **가변 길이 명령어 (CISC)** : 단순한 명령어는 1바이트로 짧게 만들고, 메모리 접근과 연산을 한 번에 하는 복잡한 명령어는 10바이트 넘게 길게 만든다. 과거에 RAM 용량이 몇 메가바이트밖에 안 되던 시절에는 프로그램 파일 크기를 최대한 압축할 수 있다는 장점이 있었지만, CPU의 제어장치(CU)가 명령어의 끝이 어디인지 매번 분석해야 해서 디코더 회로가 거대해지고 전력 소모가 심해진다.
* **고정 길이 명령어 (RISC)** : 복잡한 명령어를 아예 없애고 단순한 명령어만 남긴 뒤, 모든 명령어의 크기를 무조건 **4바이트(32비트)** 로 통일한 방식이다. 명령어 포맷이 일정하므로 제어장치 회로가 극도로 단순해지고, 전력 소모가 적으며 1클럭당 처리 속도가 압도적으로 빠르다.

### 📊 CISC vs RISC 아키텍처 비교

| 비교 항목 | CISC (Complex Instruction Set Computer) | RISC (Reduced Instruction Set Computer) |
| :--- | :--- | :--- |
| **설계 철학** | "복잡하더라도 명령어 하나로 최대한 많은 작업을 한 번에 처리하자" | "명령어를 극도로 단순화하여 1클럭에 1개씩 빠르게 해치우자" |
| **명령어 길이** | **가변 길이** (1바이트 ~ 15바이트로 제각각) | **고정 길이** (통상 4바이트 32비트로 일정) |
| **명령어 종류** | 수백 개 이상 (복잡하고 특수한 명령어가 많음) | 수십~백여 개 내외 (필수 기본 연산 위주) |
| **메모리 접근 방식** | 연산 명령어 안에서 메모리 직접 접근 허용 (`ADD EAX, [0x1000]`) | 오직 `LOAD`(읽기)와 `STORE`(쓰기) 명령어로만 메모리 접근 가능, 연산은 레지스터끼리만 수행 |
| **제어장치(CU) 구조** | **마이크로코드(Microcode) 방식** (해독 회로가 복잡하고 칩 면적이 큼) | **하드와이어드(Hard-wired) 회로** (논리 회로가 단순하여 디코딩이 초고속) |
| **소비 전력 및 발열** | **높음** (복잡한 디코더 회로에서 누설 전류와 발열 다량 발생) | **극도로 낮음** (단순한 회로 구성으로 전성비가 매우 뛰어남) |
| **컴파일러의 부담** | 낮음 (하드웨어가 복잡한 처리를 알아서 수행) | **높음** (단순한 명령어들을 소프트웨어 컴파일러가 정교하게 조합해야 함) |
| **대표 프로세서** | **x86, x86-64** (Intel Core 시리즈, AMD Ryzen) | **ARM** (Apple M시리즈, 스마트폰 AP, AWS Graviton 서버) |

과거에는 메모리가 비싸서 코드를 압축해 담을 수 있는 CISC가 대세였지만, 현대에는 메모리가 저렴해지고 **저전력·고효율(전성비)** 과 **파이프라이닝 병렬 처리** 가 서버와 모바일 전반의 핵심 과제가 되면서 RISC(ARM) 계열이 시장을 빠르게 장악하고 있다. 심지어 현대의 인텔/AMD x86 프로세서조차 겉으로는 CISC 명령어를 받지만, CPU 내부에서는 이를 RISC 형태의 잘게 쪼개진 미세 명령어(마이크로 오퍼레이션)로 변환하여 실행하는 하이브리드 구조를 취하고 있다.

## 6. 실무 개발 '아하(Aha!)' 모먼트 연결

CPU의 하드웨어 구조와 명령어 처리 방식을 모르고 개발했을 때 실무에서 마주치는 대표적인 2가지 장애 시나리오다.

### 💡 아하 모먼트 1: "MacBook에서 빌드한 도커 이미지를 AWS 리눅스 서버에 올렸더니 `exec format error`를 뱉으며 컨테이너가 즉사한다!"

최신 Mac(M1/M2/M3/M4)을 쓰는 개발자가 로컬에서 `docker build`로 이미지를 만들고 AWS 클라우드 EC2(`t3.medium`) 서버에 배포했다. 그런데 서버에서 컨테이너를 실행하자마자 아래 에러 로그 한 줄을 남기고 서버가 켜지지 않는다.

```text
standard_init_linux.go:228: exec user process caused: exec format error
```

* **원인** : CPU의 명령어 집합 구조(ISA)와 제어장치(CU)의 하드웨어 규격이 다르기 때문이다.
  * 로컬 MacBook은 **ARM(RISC)** 아키텍처 CPU를 사용한다. 따라서 로컬에서 그대로 빌드한 바이너리 안에는 ARM 제어장치만 해독할 수 있는 32비트 고정 길이 기계어 비트들이 들어있다.
  * 반면 배포 대상인 AWS `t3` 인스턴스는 인텔/AMD의 **x86-64(CISC)** 아키텍처 CPU를 사용한다.
* **하드웨어 밑바닥에서 벌어진 일** : x86 CPU가 메모리에서 명령어를 인출(Fetch)하여 제어장치(CU)로 넘겼으나, 비트 패턴 자체가 자신이 아는 x86 규격이 아니라 해석(Decode)이 불가능했다. 결국 CPU는 `"유효하지 않은 연산 코드(Invalid Opcode)"` 하드웨어 예외 인터럽트를 발생시켰고, 운영체제 커널이 해당 프로세스를 즉시 강제 종료시킨 것이다.
* **해결책** : 도커 이미지를 빌드할 때 타깃 서버의 CPU 아키텍처를 명시(`docker buildx build --platform linux/amd64`)하여 대상 CPU의 제어장치가 이해할 수 있는 기계어로 크로스 빌드해야 한다.

### 💡 아하 모먼트 2: "빠르게 처리하려고 스레드를 500개 띄웠더니, 오히려 서버 CPU가 100%를 찍으며 멈춰버렸다!"

대량의 데이터 10만 건을 빠르게 계산하기 위해 개발자가 Java의 `Executors.newFixedThreadPool(500)`으로 스레드 500개를 생성해 작업을 돌렸다. 기대와 달리 서버는 빨라지기는커녕 CPU 사용률이 100%로 치솟으며 일반 웹 요청조차 받지 못하고 먹통이 되었다.

* **원인** : **물리적 코어(Core)의 개수 한계** 와 **컨텍스트 스위칭(Context Switching) 시 발생하는 레지스터 대피 비용** 을 무시했기 때문이다.
* **하드웨어 밑바닥에서 벌어진 일** :
  1. 서버의 물리 CPU 코어가 4개라면, 동일한 1나노초 순간에 실제로 명령어를 실행(Execute)할 수 있는 스레드는 물리적으로 딱 4개뿐이다.
  2. 운영체제 스케줄러는 500개의 스레드를 공평하게 실행해 주기 위해 1초에도 수만 번씩 코어를 점유하는 스레드를 강제로 교체한다(시분할).
  3. 코어의 주인이 바뀔 때마다 CPU는 하던 연산을 멈추고, 현재 코어 내부의 **PC, IR, 범용 레지스터(AX, BX 등), 플래그 레지스터에 들어있던 중간 계산 값들을 전부 RAM(스택/TCB)으로 복사해 백업(Save)** 해야 한다. 그 직후 다음에 실행할 스레드의 이전 레지스터 값들을 다시 RAM에서 읽어와 CPU 레지스터에 덮어쓰는(Restore) 작업을 반복한다.
* **결과** : 4개의 코어가 정작 우리가 시킨 비즈니스 로직 연산(Execute)은 거의 하지 못하고, 하루 종일 **RAM과 레지스터 사이에서 상태값을 뺐다 끼웠다 하는 자리교체(컨텍스트 스위칭 오버헤드)** 만 하다가 CPU 클럭을 100% 다 써버린 것이다.
* **실무적 교훈** : 순수 CPU 연산 위주(CPU-Bound) 작업에서는 스레드 풀 크기를 무작정 늘리면 안 되며, 물리 코어 수($N$)에 맞춘 **$N$개 또는 $N + 1$개** 로 설정해야 컨텍스트 스위칭 비용을 최소화하고 최고 성능을 낼 수 있다.

### ❓ 의문점 해결 Q&A: 스레드 풀의 N + 1 공식과 백엔드에서 흔히 말하는 N + 1 문제는 같은 것인가?

결론부터 말하면 **이름만 같을 뿐 완전히 다른 도메인의 개념** 이다. 면접이나 실무 대화에서 혼동하지 않도록 두 개념을 명확히 구분해 두어야 한다.

#### 1. CPU 스레드 풀 적정 크기에서 말하는 N + 1 (성능 최적화 공식)
* **의미** : 여기서 $N$ 은 **서버의 물리(또는 논리) CPU 코어 개수** 를 뜻한다. 즉 4코어 서버라면 스레드 풀의 스레드 개수를 $4 + 1 = 5$ 개로 설정하라는 뜻이다.
* **왜 하필 1을 더해줄까?** : CPU 연산만 하는 스레드들이라도 간혹 가상 메모리 페이지 폴트(Page Fault)나 잠깐의 입출력 등으로 인해 4개 중 1개의 스레드가 아주 잠깐 멈칫(Pause)할 때가 있다. 이때 여분의 스레드 1개가 대기하고 있으면, 그 짧은 틈에도 코어가 놀지 않고 즉시 투입되어 CPU 활용률을 100%로 꽉 채울 수 있기 때문에 고안된 최적의 공식이다.

#### 2. 데이터베이스 / JPA에서 말하는 N + 1 문제 (치명적인 쿼리 버그)
* **의미** : ORM(JPA/Hibernate 등)을 사용할 때 **1번의 쿼리로 $N$ 건의 데이터를 조회했는데, 각 데이터의 하위 연관 데이터를 가져오기 위해 의도치 않게 $N$ 번의 추가 쿼리가 더 날아가서 총 $N + 1$ 번의 DB 쿼리가 실행되는 성능 장애 현상** 이다.
* **예시** : 게시글 목록 100개($N=100$)를 조회하는 쿼리 **1번** (`SELECT * FROM post`)을 날렸는데, 각 게시글에 달린 댓글들을 불러오기 위해 반복문을 돌며 댓글 조회 쿼리가 **100번** (`SELECT * FROM comment WHERE post_id = ?`) 추가로 실행되어 DB에 총 **101번($100 + 1$)** 의 쿼리 폭탄이 떨어지는 문제다. (이 부분은 추후 JPA 단원에서 `Fetch Join` 등으로 해결하는 법을 깊게 다룬다.)

| **CPU 내부 구성(ALU, CU, MAR, MBR)과 명령어 사이클 4단계** | ⭐⭐☆☆☆ **(하 / 배경지식 Base)** | 임베디드/펌웨어 직군이 아닌 일반 웹/백엔드 면접에서 "MAR과 MBR의 차이가 뭔가요?"라고 직접 묻는 경우는 거의 없다. 하지만 **PC(프로그램 카운터)** 개념을 모르면 이후에 배울 **OS의 스레드가 왜 각자의 PC 레지스터와 Stack을 따로 가져야 하는지**, 그리고 **JVM의 PC Register가 무슨 역할을 하는지** 이해할 수 없으므로 반드시 잡고 가야 하는 뿌리 지식이다. |

### 🎯 면접을 위해 반드시 머릿속에 남겨야 할 핵심 질문 2가지

1. **"멀티스레드 환경에서 스레드 개수를 무작정 늘리면 왜 오히려 성능이 떨어지는지, CPU 코어와 레지스터 관점에서 설명해 보세요."**
   * **핵심 답변 포인트** : 물리적으로 동시에 명령어를 실행할 수 있는 개수는 **물리 코어(Core)의 수** 로 제한되어 있다. 스레드가 코어 수보다 과도하게 많으면 OS 스케줄러가 스레드를 빈번하게 교체하는 **컨텍스트 스위칭(Context Switching)** 이 발생한다. 이때마다 CPU 내부의 **PC(프로그램 카운터)와 범용 레지스터들에 담긴 연산 중간 상태값을 RAM(TCB/스택)에 저장하고 새 스레드의 값을 복원하는 하드웨어 오버헤드** 가 발생하며, CPU 캐시까지 초기화되어 정작 연산에 써야 할 클럭을 문맥 교환에 다 낭비하게 된다.

2. **"프로그램이 실행될 때 CPU의 PC(Program Counter) 레지스터는 어떤 역할을 하며, 왜 중요한가요?"**
   * **핵심 답변 포인트** : PC는 **다음에 실행할 기계어 명령어의 메모리 번지(Address)** 를 기억하는 레지스터다. 명령어를 인출(Fetch)할 때마다 다음 주소로 자동 증가하며 프로그램의 실행 흐름을 이끈다. 특히 멀티스레드 환경에서 컨텍스트 스위칭이 일어났다 돌아왔을 때, 해당 스레드가 **"아까 코드의 몇 번째 줄까지 실행했었는지"** 를 기억하고 이어서 실행할 수 있게 해주는 핵심 하드웨어 요소다.

### 💻 개발 과정을 이해하기 위해 챙겨야 할 감각
* **도커(Docker)나 서버 환경을 다룰 때** : 내 로컬 개발 PC(Mac ARM 등)와 실제 운영 배포 서버(Linux x86 또는 ARM)의 CPU 아키텍처가 같은지 확인하는 습관을 들여야 한다. 우리가 짜는 코드는 결국 타깃 CPU의 제어장치(CU)가 해독할 수 있는 0과 1의 기계어로 번역되어야만 실행된다.
* **비동기 처리나 스레드 풀(Thread Pool)을 설정할 때** : `newFixedThreadPool(숫자)`에 아무 숫자나 넣지 말고, **"이 작업이 CPU 연산만 계속하는 작업(CPU-Bound)인가, 아니면 DB/외부 API 응답을 기다리는 작업(I/O-Bound)인가?"** 와 **"내 서버의 물리 코어가 몇 개인가?"** 를 먼저 확인하고 스레드 수를 결정하는 엔지니어링 감각을 가져야 한다.
